## ② 量法裁定（专节）

### 2.1 AC-R1 留白量法 —— **接受新口径**

**(1) 原量法是否真错？——是，两路独立证据。**

`3e2816b:app.css` 层级（实证）：`.shell`(L50,`display:flex`) > `.sidebar`(L55,`width:210px;flex:none`) + `.main`(L156,`flex:1;display:flex;flex-direction:column`) > `.content`(L195)。**`.content` 的坐标空间是 `.main`，210px 侧栏在 `.main` 之外。**

- **证据 A（结构性）**：原量法 `autoLeft = content.rect.left`（含侧栏 210），`autoRight = docEl.clientWidth − content.rect.right`（不含侧栏）。左右两项不在同一坐标系。
- **证据 B（数值判死，我亲自复算）**：在**候选代码**（已 `margin-inline:auto`）上跑原量法：
  ```
  1920：left 584.28 ; right 1905−1530.38 = 374.62 → 差 209.66
  2560：left 904.28 ; right 2545−1850.38 = 694.62 → 差 209.66
  ```
  两档**完全相同、恒定 209.66 ≈ 210 − 0.35**（0.35=半像素取整），与 `cdp-ac-diag.log` 实测 `209.64999…` **逐位一致**。

> **决定性论证**：真正的未居中误差**必须随视口变宽而增大**（红端实测 385→1040）。而原量法在**已经居中**的代码上给出**与视口无关的常数 210**——这是「左侧恒多一个侧栏宽」的指纹。**原量法测的不是居中，是侧栏。**

**新量法**（`cdp-ac.mjs` `mainGap`）：`l = rect.left − main.left`、`r = main.right − rect.right`、`diff = |l − r|` —— 同坐标系，正确。

**(2) 红端 385/1040 是否仍有效？——能，但必须重新表述。**

原量法红端读数不能照搬（含 210 系统偏差）。我把新口径**代数套用**到红端原始读数（red.log `F0` 行有 `rectLeft/rectRight/padding`）：

| 档 | 红端 `.content` rect | 内容区宽 = rect −64 | 新口径左留白 | 右留白 | 新口径 diff |
|---|---|---|---|---|---|
| 1920 | 210 / 1310 | 1036 | 210−210 = **0** | **1036 − 652 = 384** | **384** |
| 2560 | 210 / 1310 | 1036 | **0** | **1036 − 652 = 384** | **384** |

> ⚠️ **复查纠正**：红端两档 diff 其实是**同一个 384**，不是开发员所称的 385/1040。因 `.reader-split` 两档 rect 完全相同（`left 242 / right 1278`），正文列从不随视口变宽——**红端缺陷不是「留白随视口增长」，而是「内容钉在左边、右侧恒空 384px，多出的视口宽全落在 `.content` 之外」**。原量法 385/1040 的差额**全部来自视口宽差（595 vs 1250）**，是侧栏坐标错位的产物。

**因此红端证据的准确表述应为**：「`.main` 内左留白恒 0、右留白恒 384px；视口从 1920 增至 2560 时，多出的 640px **全部变为 `.content` 外的空白**，内容区纹丝不动」。这与用户原话「全屏时右侧一大片空」**比开发员的数字更贴切**，且不依赖任何拆解。

**开发员的「真差 165 / 830」拆解：不采信。**其自测 §5.1 的 `165 = 1710 − 2×Δ…严格拆解：` 是**未完成草稿**留在交付物里，且拆解前提（「剔除侧栏后还差 165/830」）与上表的 384/384 不符。**本审查不引用 165/830。**

**(3) 新量法是否更严？——是。**

新判据 `diff = |l−r| ≤ 2` ⟹ `2×留白 + W ≈ mainWidth`（闭合约束，误差 ≤2px）；旧判据 `|left − (V−right)| ≤ 2` **不含** `W` 与 `mainWidth` 的闭合项，在含侧栏坐标系里 `2×留白+W` 可随意偏离。**净结论：新量法更严，接受。**（开发员的 1710 算式方向对、细节不严谨，不引用。）

**(4) 是否要补「新量法在修复前复现红」？——不需要。** 第 (2) 节已用红端原始读数**纯代数**重算完毕，无需重编译父候选。**不作驳回项。**

`.reader-body` 实测 **498.09px（47.74ch）**，远低于 `66ch=688.65`。几何推导（全部基于实测读数）：

```
绿端 1920：.content clientWidth 946 → 内容区 946−64 = 882
```

**为何不是 688.65**：`minmax(0, 66ch)` 的 max 是**上限**而非目标值；`66ch` 在本项目**从未触顶**（实测 498 / 红端 652）。左列实际宽由容器决定。→ 开发员自测 §二「498.094（`minmax(0,66ch)` 封顶）」**表述错误**（B-1）。
