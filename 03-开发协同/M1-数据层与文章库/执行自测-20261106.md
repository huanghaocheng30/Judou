### AC1-d 克隆复核（发现并修掉一个「只在克隆里才会红」的门禁缺陷）

第一次克隆复核（`git clone file:///E:/Judou` 后跑同一脚本）**exit 1**：

```
文件数: 13（期望 13）｜`_` 前缀中间件: 0（期望 0）
字节总数: 3529547（期望 3529547）      ← 内容包字节没问题
cet4-2023-12-set1-passageA.json | 243367 | 8d653d9662f0 | FAIL
…（13 个全 FAIL）
FAIL: 内容包落位与设计区不一致
```

根因（实测定位）：本机 `core.autocrlf=true`。`02-代码/.gitattributes` 里的 `content-pack/** -text`
只钉住了内容包一侧（克隆后仍是 6,912 B 的 LF），而 `01-设计/…/内容包/` 的 JSON 在 `git clone` 时
被 checkout 转成 CRLF（设计区 `manifest.json` 从 6,912 B 变大到 7,160 B）。于是**内容一致但行尾不同**，
旧判据（裸 SHA-256）把它误判成「内容不一致」。

修法（commit `e9ca887`）：`verify-pack.mjs` 把「raw 逐字节一致」与「仅 EOL 差异」分开计数，
只有**内容（EOL 归一后）**不同才 FAIL；字节总数 / 无 `_` 中间件 / manifest 12 篇三条判据不变。
**没有动 `.gitattributes`**（`content-pack/** -text` 是 M0 已就位且正确，内容包侧字节必须钉死）。

修后克隆复核：

```
verify-pack in clone EXIT=0

内容一致: 13/13（其中 raw 字节一致 0，仅 EOL 差异 13）
  提示：13 个文件仅行尾不同——这是 checkout 策略造成的（`git clone` 到 core.autocrlf=true 时，
        设计区 JSON 被转 CRLF，而 content-pack 被 .gitattributes 的 -text 钉住）。内容本身一致。
PASS: 13/13 文件内容一致（raw 0 + 仅 EOL 13）｜3529547 B｜无 `_` 中间件｜manifest 12 篇齐全
```

**结论：通过**。进程未崩（CDP 仍可连、窗口在）、错误页只有 basename、无绝对路径、未落进空文章库；
且「随包分发的 3,529,547 B」在干净克隆里**逐字节仍是 3,529,547 B**。
