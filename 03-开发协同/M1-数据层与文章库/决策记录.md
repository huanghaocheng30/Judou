## 一、任务包生成阶段的裁定（调度员，2026-11-05）

| # | 问题 | 裁定 | 依据 |
|---|---|---|---|
| 1 | 内容包里的 `token.isWord` 在 M0 建的 `token` 表里**没有对应列**（docs C2 §4.5 明确无该列，只建议「MVP 可用 `normalized` 是否含字母数字判断」） | **走 `002` 迁移加 `token.is_word` 列，落内容包权威值**；不用 `normalized` 推导 | 实测：选词填空的空格 token 是 `{"surface":"26","normalized":"26","isWord":false}` —— 按 `normalized` 含数字推导会判成「词」，**30 个空格全部丢失**；而正文固有数字（`150`/`1997`/`88,000`）必须不判为空格。唯一可靠来源是内容包的 `isWord` |
| 2 | `article` 表缺 `pack_version` 与 `sentence_count`，但 05 §二 要求「`article.pack_version` 写 manifest 值」、05 §三 要求卡片五项字段取冗余 `sentence_count` 避免 N+1 | **同批 `002` 迁移加上这两列** | ① 单一版本权威需要落点（否则每次启动都要读 manifest 比对，且无法回答「库里是哪版」）；② 句数走冗余列避免 12 篇 × N 次子查询 |
| 3 | `001_init.sql` 是否直接改（M0 刚建，尚未有真实用户数据） | **不改，一律走 `002`** | docs D1 §11.6「已发布迁移不得修改」；M0 已置「已完成」并进 git 历史，改 001 会让后续所有迁移不可信。AC2 用 `git status` 守住 |
| 4 | 12 篇内容包的 `packVersion` 全是 `2023-12-set1-v0.9`（连 set2/set3 篇也是），是否入库 | **不入库、不参与比较**；唯一权威是 `manifest.packVersion = 2026.11.05-1` | 05 §二 规则 1；实测 12/12 篇残留值相同，若入库会导致 set2/set3 篇永远「版本相同」而跳过更新 |
| 5 | `manifest.json` 不存在（内容包目录只有 12 篇 + 分片） | **由调度员生成**（内容资产，属设计区，不涉目标代码区） | 05 §二 输入契约要求 `manifest.json`；已按实测算出 12/90/274/6699 + 274/213/1561/30/90 并写入 `totals` |
| 6 | 本包包切：导入 + 文章库 + 精读只读，是否再拆 | **不拆，单包大包档位（C≤8/B≤8/工作轮≤48）** | 三者共用同一套数据通道（导入 → 查询 → 渲染），拆开会让第二个包重复搭桩；且「文章库能看到 12 篇 + 能点进一篇」构成一次有意义的人工测试 |
