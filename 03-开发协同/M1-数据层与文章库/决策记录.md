## 一、任务包生成阶段的裁定（调度员，2026-11-05）

| # | 问题 | 裁定 | 依据 |
|---|---|---|---|
| 1 | 内容包里的 `token.isWord` 在 M0 建的 `token` 表里**没有对应列**（docs C2 §4.5 明确无该列，只建议「MVP 可用 `normalized` 是否含字母数字判断」） | **走 `002` 迁移加 `token.is_word` 列，落内容包权威值**；不用 `normalized` 推导 | 实测：选词填空的空格 token 是 `{"surface":"26","normalized":"26","isWord":false}` —— 按 `normalized` 含数字推导会判成「词」，**30 个空格全部丢失**；而正文固有数字（`150`/`1997`/`88,000`）必须不判为空格。唯一可靠来源是内容包的 `isWord` |
| 2 | `article` 表缺 `pack_version` 与 `sentence_count`，但 05 §二 要求「`article.pack_version` 写 manifest 值」、05 §三 要求卡片五项字段取冗余 `sentence_count` 避免 N+1 | **同批 `002` 迁移加上这两列** | ① 单一版本权威需要落点（否则每次启动都要读 manifest 比对，且无法回答「库里是哪版」）；② 句数走冗余列避免 12 篇 × N 次子查询 |
| 3 | `001_init.sql` 是否直接改（M0 刚建，尚未有真实用户数据） | **不改，一律走 `002`** | docs D1 §11.6「已发布迁移不得修改」；M0 已置「已完成」并进 git 历史，改 001 会让后续所有迁移不可信。AC2 用 `git status` 守住 |
| 4 | 12 篇内容包的 `packVersion` 全是 `2023-12-set1-v0.9`（连 set2/set3 篇也是），是否入库 | **不入库、不参与比较**；唯一权威是 `manifest.packVersion = 2026.11.05-1` | 05 §二 规则 1；实测 12/12 篇残留值相同，若入库会导致 set2/set3 篇永远「版本相同」而跳过更新 |
| 5 | `manifest.json` 不存在（内容包目录只有 12 篇 + 分片） | **由调度员生成**（内容资产，属设计区，不涉目标代码区） | 05 §二 输入契约要求 `manifest.json`；已按实测算出 12/90/274/6699 + 274/213/1561/30/90 并写入 `totals` |
| 6 | 本包包切：导入 + 文章库 + 精读只读，是否再拆 | **不拆，单包大包档位（C≤8/B≤8/工作轮≤48）** | 三者共用同一套数据通道（导入 → 查询 → 渲染），拆开会让第二个包重复搭桩；且「文章库能看到 12 篇 + 能点进一篇」构成一次有意义的人工测试 |

> 来源：`计划评审-v1.0.md` §六.1 B1~B10 + §六.2 独立裁定。B9/B10 由审核员明确交调度员裁决（规范 §3.8 规则③）。

| # | 问题 | 裁定 | 依据与代价 |
|---|---|---|---|
| 7 | **B9 债务归属三方不一致**：M0 验收结论判 T1/T2/T3/T6「转 M1」，`Import.tsx:9` 注释写「M5 处理」，02 §八 顺延 M5 且理由与 T2 的实际泄漏面矛盾 | **拆开处理**：T1（路径限域）+ T2（错误信息 basename 化）**M1 收口**；T3（旧版残留清理）**顺延 M5**；T6（错误类型契约）**并入 B10 当场收口** | T1/T2 —— M1 正是第一次读 `manifest.articles[].file`、第一次定义内容包错误类型的包，泄漏面在本包已成立；各 1~2 行（`file` 解析后必须落在包目录内；`StartupError::PackCorrupt{file}` 只回 basename），不做等于把已知风险留给用户导入阶段才修。T3 —— 本包只导入首版内容包、无旧版残留，顺延不产生实际风险 |
| 8 | **B9 附带的红线陷阱**：T3 若用 `DELETE FROM article` 清理旧版行，会经 001 的 `ON DELETE CASCADE` 删掉 5 张用户表 + 把 `vocab_entry.source_article_id` 置 NULL（`db.rs:30` 已开 `foreign_keys=ON`） | **写死口径：内容包导入（含未来版本升级）只允许 `INSERT` / `UPDATE`，禁止 `DELETE` 任何内容表行**；需要「失效篇」时只能把 `status` 置 `draft`（001 已有该列） | 这是数据安全的硬边界，不是风格偏好。落实在 02 D3 与 `import.rs` 注释；审核员在代码审查时按此条核查 |
| 9 | **B10 类型名不一致**：02 D2 写 `PackError`，05 §二 规则 6 写 `StartupError` | **采用 `StartupError`**（服从冻结设计 05 §二），M2~M5 沿用同一名 | 05 是设计基线冻结文件；本包是第一次定义该类型，改名成本为零。反向保留 `PackError` + 别名会让 M2~M5 每包都要解释一次。附带要求：**必须 `impl std::error::Error`**（`lib.rs` setup 闭包用 `?`，不实现则编译不过） |
| 10 | **B8 内容包缺失/损坏时无错误页**：04 §6.8 表格 header 明标「M0/M1」，要求「显示缺失/损坏文件名 + 请重新安装，不进入空壳目录」；02 只做到「不 panic」 | **M1 做最小错误页**（选 (a)）：`src/App.tsx` 增启动态分支，`startupError` 非空时整页显示原因 + 文件名 + 「请重新安装」 | 代价是全包多改 1 个前端文件（约 15 行）；换到的是「坏包启动即空文章库、用户完全不知道发生了什么」这个最坏形态被消除。04 §6.8 已把该行为写进 M0/M1 范围，顺延需要改设计文档，成本高于直接做 |
| 11 | **B4 `article.source` 无权威取值**：12/12 篇 `meta` 无 `source`、manifest 无 `source`；但需求说明 F2 与 05 §三 都要求「来源」筛选 | **`source = 'CET-' + <examType 数字> + ' ' + examYear + '年' + examMonth + '月真题'`**，`examMonth` 取篇内 `meta.examMonth`（实测 12/12 有值 = 12） | 现行 12 篇实际值全为 `CET-4 2023年12月真题`，唯一期望值 → AC5 可判定。选「年月真题」而非常量：真实考试每年两场（6 月/12 月），`examMonth` 是既有事实字段，未来加 2024-06 篇时来源筛选项自然长出第二项；用常量则永远只有一项、筛选器形同虚设。注：04 §八/§10.1 只列三个筛选器，与需求说明 F2 + 05 §三 不一致，**以需求与 05 为准，04 属待同步的文档差异**（登记在 02 D4） |
