## 二、产品定位、目标用户、核心流程

### 2.1 定位【A/B 混合】

- **一句话定位**：以「大量可理解输入（comprehensible input）」为方法论的**多语言沉浸式阅读器 + 词汇状态追踪系统**，不是词典、也不是刷题工具。【C 推断，依据 S1 的状态模型与 S5 的免费/付费分层】
- **商业形态**：商业闭源订阅制产品，官方客户端覆盖 Web / iOS（S13）/ Android（S11），另有三方浏览器扩展生态（S1、S4、S14）。【A：S13 存在；S5 标题证明有付费层】
- **核心资产不是内容，而是「词状态」**：LingQ 把每个学习者对每个词的掌握度存成账号级数据，阅读时按状态着色。这是它区别于普通阅读器的关键。【A：S1 明述「status syncs straight back to your LingQ account」「styled by word status」；C：账号级持久化由 S1 的同步行为推得】

### 2.2 目标用户

- **主目标**：以「兴趣内容驱动」学外语的自主学习者，愿意长期投入、追求词汇量增长，而非应试冲刺。【C 推断，依据其方法论与状态统计导向】
- **与本产品用户的差异**：LingQ 用户要的是「长期浸泡 + 词汇量」，本产品用户要的是「一篇真题吃透 + 考前复盘」。**同一交互形态（点词查义）背后的目标不同**，这决定了抄什么、不抄什么（见第八、九节）。

### 2.3 核心流程【A 部分 + C 部分】

可核实的一段（来自 S1 对 LingQ 机制的复刻）：

```
阅读原文 → 词按掌握状态着色 → 点某个词 → 弹窗给出译文/提示
        → 在弹窗内一键改该词状态（New / Learning / Known / Ignored）
        → 状态同步回账号 → 下次阅读时该词的呈现随之变化
        → 用户也可划选一个短语 → 加入追踪并查看译文
```

关键结构性事实：**LingQ 的默认阅读态是「词本位」的**——点词的响应是即时的、轻量的、就地弹窗的；句子能力（Sentence Mode）是**另一个独立模式**，不是默认阅读态的默认点击行为。【A：S1 描述的点词链路；B：S6 标题「Sentence Mode: How & why to use it」证明其为独立功能单元；C：由二者并存推得「模式切换」而非「同层交互」】

> 这一条是本次调研对本项目**最重要的结构性发现**，详见第八、九节。

## 四、交互模式

> 本节按派工要求逐项回答「点词/点句后发生什么、面板位置、层级关系、移动端手势与滚动行为」。凡无证据处直接标【缺口】，不做美化推测。

### 4.1 点词后发生什么【A，依据 S1】

| 步骤 | 行为 |
|---|---|
| 触发 | 点击（tap）已着色的词 |
| 呈现 | **就地弹窗（popup）**，锚定在该词附近，内容＝译文 + LingQ 的「hints」 |
| 弹窗内可做的事 | ① 读译文/提示；② 一键改该词状态（New/Learning/Known/Ignored）；③ 按 `X` 忽略该词；④ 按 `ESC` 关闭 |
| 导航 | `←` / `→` 跳到**下一个未知词**（不关闭弹窗，连续处理） |
| 副作用 | 状态变更**立即同步回账号**，原文该词的着色随之改变 |

**形态结论**：这是**轻量浮层（popover/popup）**，不是抽屉、不是固定侧栏。它的设计前提是「一次只处理一个词、内容量小、处理完立刻回到阅读」。【A：S1 的交互描述；C：形态归类】

### 4.2 点句后发生什么【B + 缺口】

- **有据**：LingQ 存在名为 **Sentence Mode** 的独立功能（S6 标题），其定位是「怎么用、为什么用」——说明它是**一种可切换的阅读模式**，而非「点一下就出结果的默认交互」。【B】
- **有据（反向）**：移动端用户曾发帖问 **「How to see sentence translation in app?」**（S7）——这反证：句译在移动端**不是显而易见的一级交互**，用户需要求助才能找到。【B】
- **【缺口】**：Sentence Mode 的进入方式、面板位置（全屏/抽屉/底部）、是否与原文同屏对照、是否支持逐句切换与朗读——**全部未取得正文**，不作结论。

### 4.3 面板位置与形态对比（对本项目直接相关）

| 形态 | LingQ | 证据 | 与本产品骨架的关系 |
|---|---|---|---|
| 词解析 = 就地气泡弹窗 | ✅ 是 | 【A】S1 | 本产品「点词」若也要气泡，需注意：气泡适合「一段译文」，不适合「语境义+音标+词性+搭配+例句」五块内容 |
| 句解析 = 独立模式（非浮层） | ⭕ 疑似 | 【B】S6/S7 | 本产品「点句 → 底部半屏抽屉」是**另一种解**：把句级内容放在同屏浮层里，不切换模式 |
| 桌面右侧固定栏 | 【缺口】 | — | LingQ 官方是否采用侧栏**无证据**；本文不给「LingQ 也用侧栏」这种结论 |

### 4.4 层级关系【C 推断】

依据 S1 的「划选短语 → 加入追踪」可推：LingQ 的粒度层级是 **词 → 短语 →（模式级的）句**，其中**短语是用户手动圈出来的**，不是系统预置的语法单位。这与本产品「系统预置短语/固定搭配」是两条不同路线（见第九节启示 3）。

## 五、优点 / 限制 / 用户反馈线索

### 5.1 优点（有据可查）

1. **词状态是产品骨架，不是附属功能**【A】。四态（New/Learning/Known/Ignored）+ 账号持久化 + 即时反馈（`←`/`→` 连续处理未知词），构成一个「读—标记—再读」的闭环。这套机制让「阅读」和「词汇管理」在同一屏内完成，不需要切到生词本。【A + C】
2. **处理未知词的路径极短**【A】。点词 → 读译文 → 按键分类 → 下一个词，全程不离阅读上下文，是它最值得学的交互效率设计。
3. **短语级追踪**（S1）【A】。允许用户圈选跨词片段并加入追踪，解决了「词组不等于单词」的问题。
4. **跨端一致的状态**（S1 的同步语义）【A】。

### 5.2 限制

1. **默认态不含句级解析**（S6/S7）【B】。句子能力被隔离成模式，移动端用户甚至找不到句译入口——对本项目是「差异化机会」，不是「要追平的能力」。
2. **无逐句语法结构拆解的证据**【缺口】。长难句「哪是主句、哪是从句」这类需求，LingQ 的产品叙事里未见对应物。
3. **强依赖在线账号**【C】。状态同步与「换设备即用」是其卖点，反过来说明「无账号、纯离线」不是它的设计目标——与本产品的约束（无账号、全离线）是**架构级分歧**。
4. **Reader 交互反复重构**【B：S9/S10/S11】。既有用户抱怨快捷键被改坏，说明其交互尚未收敛。

## 九、对本项目启示（逐条标注 事实 / 推断 / 建议）

> 标注规则：**事实**＝本报告已取证；**推断**＝由事实推演、未直接验证；**建议**＝给设计决策的取向，需调度员/用户裁决。

### 启示 1 · LingQ 是「词本位」，本产品是「句本位」，这是结构性差异而非功能差距

- **事实**：LingQ 默认阅读态的点按对象是**词**，句子能力是独立模式（S6/S7）【A/B】。
- **事实**：本产品首版骨架是「点句 → 底部半屏抽屉（句译/语法/短语）＋ 点词 → 同一抽屉内切换」。
- **推断**：同类产品（至少 LingQ 这一支）没有把「句级解析」当作一级交互来解，因此**本产品在交互形态上没有可直接照抄的成熟范本**，需要自己承担设计成本。
- **建议**：把「点句」当第一入口、点词为二级（在抽屉内切换）的决策**可以维持**；但要在 04 方案中明确写出「句级抽屉的信息密度上限」——若一个抽屉要塞句译+语法+短语+词义五块，半屏会不够，需提前定「分段/折叠/滚动」策略。

### 启示 2 · 「半屏抽屉」与 LingQ 的「就地气泡」是两种不同赌注，各有代价

- **事实**：LingQ 词解析是**锚定在词上的轻量气泡**（popover）【A】。
- **推断**：气泡的优点是「不遮挡上下文、不打断视线」，代价是「放不下多块结构化内容」；抽屉的优点是「内容容量大、结构清晰」，代价是「必然遮挡原文下半屏，且要处理滚动与关闭手势」。
- **建议**：本产品的句级内容量显然超出气泡容量，选抽屉是合理的。但**必须解决「抽屉打开时当前句是否仍可见」**——建议抽屉高度上限设为 50~60% 屏高，并在打开时把当前句**滚动到抽屉上沿以上**（必要时加一句「已为你定位到当前句」的视觉锚）。此点属设计决策，需用户确认（对应 01 文档 Q1/Q2）。

### 启示 3 · 短语：系统预置是主路，用户自选应预留数据能力

- **事实**：LingQ 允许用户**划选短语**并加入追踪、查看翻译（S1）【A】；未见「系统预置固定搭配讲解」的证据【缺口】。
- **推断**：系统预置短语必然有漏（真题里的搭配千变万化），如果数据结构只能存「系统给的短语」，二期加「用户自选短语」时要改表。
- **建议**：首版 UI 只呈现系统预置短语（符合 F2），但**数据模型上把「短语」与「短语来源（系统/用户）」分开**，并在 token 层预留「可跨 token 选择的短语区间」表示法。成本极低，避免二期返工。

### 启示 4 · 生词本应从「收藏」升级为「状态」，但首版可折中

- **事实**：LingQ 用四态（New/Learning/Known/Ignored）表达词掌握度，且状态即时影响阅读呈现【A】。
- **推断**：本产品 F5 若只有「收藏/取消收藏」，用户会遇到「这个词我见过三次还是记不住」与「这个词我已经会了但还躺在生词本」两种失真。
- **建议**：首选实现三态（生词 / 在学 / 已掌握）+ 忽略；若首版预算紧，至少把**状态字段**建进表（值可为空），UI 先只暴露「收藏」。避免二期改表迁移。

### 启示 5 · 离线预生成带来的「语境义」是 LingQ 架构上做不到的，这是本产品的真护城河

- **事实**：LingQ 的词译文是账号在线体系下的产出，其数据单位是「词 × 用户 × 状态」【A】。
- **事实**：本产品的数据单位是「token × 所在句」（01 文档 §七：词义挂 token 层且绑定所在句子）。
- **推断**：同词不同句给不同释义，需要「为每篇文章的每个 token 逐一生成」的离线流水线；这在以「海量内容 + 实时查词」为模式的 LingQ 里是成本不可接受的，而在本产品「少量真题 + 深度解析」的模式里是可行的。
- **建议**：这应当写进 04 方案的「与替代方案的差异」并被当作**核心卖点**，而不是一个技术细节。相应地，**解析质量的抽检**（01 文档 Q3）优先级应高于任何界面打磨——若语境义错了，护城河立刻变成负资产。

### 启示 6 · 语法拆解是供给空白，但要警惕「过度承诺」

- **事实**：本次**未取得任何证据**表明 LingQ 提供句级语法结构拆解（主干/从句/修饰关系）【缺口】。
- **推断**：这既可能是「没人做」，也可能「做过但用户不需要」；现有证据无法区分（LingQ 论坛不可达，无法查证用户是否抱怨「缺少语法」）。
- **建议**：把语法拆解作为差异化能力保留（它是用户原始需求的原话），但**首版对拆解的形态保持克制**：先做「主干句 + 从句/修饰块的分层高亮 + 一句话结构说明」，不要一上来做依赖树式的语法树图——后者生成与校验成本极高，而四级用户的真实需求是「看懂这句在说什么」。

### 启示 7 · 颜色/标记必须双通道，且要有图例

- **事实**：LingQ 用户发帖表示不懂蓝词黄词的含义（S8）【B】。
- **建议**：本产品若用颜色标记「四级高频词 / 生词 / 短语」，一律配文字或图标；首次进入阅读页给一次性图例；对色觉障碍保留可用性（不只靠色相区分）。此为可访问性要求，不可省。

### 启示 8 · 阅读器是高频返工区，首版交互要「少而稳」

- **事实**：LingQ 在 Web 与 Android 两端都做过 Reader 大重构，且重构引发快捷键退化抱怨（S9/S10/S11）【B】。
- **推断**：阅读器一旦被用户形成肌肉记忆，改动成本极高；而「一次做对」几乎不可能。
- **建议**：首版把交互面收窄到两个动作（点句、点词）+ 一个关闭方式，**不引入手势隐藏功能**（如长按选短语、双击收藏），把手势留给二期；并在 04 方案里显式写「本版不做的手势清单」，避免实现期临时加。

### 启示 9 · 移动端「入口可见性」比「功能完备」更致命

- **事实**：LingQ 移动端用户需要发帖问「怎么在 App 里看句译」（S7）【B】。
- **建议**：本产品移动端**不能有任何隐藏的解析入口**——点句子就是唯一、显式、无需发现的入口；抽屉关闭后原文要有「此处可点」的轻提示（首篇首次出现即可）。这一条应作为验收项写进任务包 AC。
