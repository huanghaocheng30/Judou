> 用途：为「后续以哪套设计为准」提供裁决依据。**本文只做对照与建议，不改任何既有设计件**。
> 对照对象：`E:\Judou\docs\`（16 份，2026-11-04 定稿）↔ `01-设计/CET4-阅读精读/`（01~06 + 原型 + 任务包，2026-11-05 定稿）

## 一、一句话结论

**重合约六成（骨架、数据四层、偏移口径、生词/笔记/进度、不做判分），硬冲突 5 处（定位、技术栈、数据模型、页面骨架、包切分），docs 独有 10 块（复习/标签/统计/导出/设置/发布/导入规格/命令清单/测试/风险），我们独有 6 块（解析三表与渲染规格、1561 词库与降级链路、空格解析、内容包结构、可复算守卫、多考试字段）。**

**建议：以 docs 为主干合并重写**（方案 A）。理由：docs 的工程体系（C2 数据模型 / C3 命令清单 / C4 导入规格 / D3 测试 / C5 发布 / F2 风险 / E2 许可）是我们完全缺失且重写代价高的部分；我们独有的 6 块是「内容资产 + 渲染规格」，作为增量并入比反过来补工程体系便宜一个数量级。

## 三、硬冲突（必须裁决，每处都有后果）

### 冲突 1 · 产品定位：平台是否提供解析
- **docs**：[A1 §2.2](docs/A1-项目定义卡.md)「不是 AI 解析器：平台不生成句译、语法、词义，笔记由用户写」；§2.3 把「AI 阅读解析工具」列为**要避开的替代方案**；ADR-011 同义。
- **我们**：04 §13.3「句级六段式（不可偏离）」+ 13.4 词库，已产出 **274 句 × 六段 + 213 张词卡 + 1561 词库 + 30 空解析**。
- **裁决（用户已定）**：**预置解析 + 用户笔记双线**——平台给高质量人工解析，用户可叠加自己的笔记。
- **后果**：A1 §1/§2.2/§2.3、ADR-011 需改写；「与替代方案的差异」表中「AI 解析工具」一行必须换成「本产品＝**人工校订**的预置解析，非 AI 生成」（这是差异点而非短板）。C2 必须新增解析三表（见冲突 3）。

### 冲突 2 · 技术栈：React 还是原生 DOM
- **docs**：ADR-005 明确 **React + Vite + TypeScript**；C1 §4.1 有前端分层。
- **我们**：04 §9 / TP1 §二 明确 **原生 DOM，不引入 React/Vue**（当时理由是「与原型实现一致、包更小」）。
- **裁决（用户已定）**：**React**（配合 oil-ui 重构）。
- **后果**：TP1 前端 772 行（`src/router.ts`、`pages/*.ts`、`render/tokens.ts` 的 DOM 层、`styles.css`）作废重写；`renderTokens` 纯函数的**逻辑与断言可保留**（它不依赖 DOM，只是产出节点数组），这点能省不少返工。Rust 侧 1133 行里 `db.rs`/`import.rs`/`articles.rs` 的 schema 与命令要按 C2/C3 调整，但事务与幂等骨架可留。

### 冲突 3 · 数据模型：15 表 vs 10 表，两边都缺一半
- **docs 15 表**：`schema_meta` / `article` / `paragraph` / `sentence` / `token` / `question` / `sentence_note` / `word_note` / `vocab_entry` / `tag` / `vocab_tag` / `review_plan` / `review_log` / `reading_record` / `app_setting`
- **我方 10 表**（TP1 已落库）：`app_meta` / `article` / `paragraph` / `sentence` / `token` / `sentence_analysis` / `token_analysis` / `lexicon` / `question` / `blank`
- **差集**：
  - **我们要补 5 张**：`sentence_note`、`word_note`、`vocab_entry`(+`tag`/`vocab_tag`)、`review_plan`/`review_log`、`reading_record`、`app_setting`（`app_meta` 与 `schema_meta` 职责重叠，合并为一个）
  - **docs 要补 3 张**：`sentence_analysis`（274 行）、`token_analysis`（213 行）、`lexicon`（1561 行）；另 `blank` 可由 `question`+`blankNos` 承载，也可独立成表
  - **字段口径冲突**：docs 用 `id INTEGER AUTOINCREMENT` 代理键 + 外键；我方用业务键复合主键（`sourceKey`+`idx`）。**必须统一**——建议采 docs 的代理键（理由：笔记/生词/复习都挂在 `sentence_id`/`token_id` 上，业务键复合会把这些表的外键变成三列，级联与索引都变复杂）。
- **后果**：数据库需按合并后的 ~19 表重建 `001_init.sql`；TP1 已导入的本地库作废（用户已卸载，零损失）。

### 冲突 4 · 页面骨架：8 页带导航壳 vs 2 页无壳
- **docs**：A2 §4.1 八页（首页/今日、文章库、精读页、生词本、复习、导入、记录、设置）+ 底部导航（移动）/侧边栏（桌面）。
- **我们**：04 §七 四节（文章库、阅读页、生词本、设置）——**没有首页/今日、没有复习、没有导入、没有记录**，且没有导航壳（原型是「总目录 → 篇目 → 返回」两级）。
- **后果**：前端要从「两级页面」改成「导航壳 + 8 页」，这正是用户说「前端设计不合理」的根因——不是配色问题，是**信息架构缺一层**。原型 13 页作废，按 oil-ui 重做。

### 冲突 5 · 包切分：M0~M7（按能力）vs TP1~TP5（按人工测试）
- **docs F1**：M0 骨架 → M1 数据层与展示 → M2 精读闭环 → M3 生词本 → M4 复习 → M5 导入 → M6 导出与记录 → M7 发布链路（占比 5/15/20/12/10/15/10/13%）。
- **我们**：TP1 骨架与导入 → TP2 句卡 → TP3 词卡 → TP4 题目与空格 → TP5 笔记/生词/恢复。
- **判断**：docs 的 M0~M7 粒度更合理（每个 M 都是一次有意义的验收），我们的 TP2/TP3/TP4 其实都在「精读页」内，三包加起来才抵 docs 的 M2。**建议采用 M0~M7 作为包骨架**，把我们的解析/词库/空格三块塞进 M2，把复习/导入/记录按 docs 顺序排。
- **后果**：TP1 作为「M0+M1 的一部分」保留成果（骨架 + 导入 + 只读展示），TP2 之后按新骨架重排（TP2 改名/重定义，不影响已完成的工作）。

## 六、三个基线方案（成本/收益）

### 方案 A · 以 docs 为主干合并重写（推荐）
- **做法**：以 docs 的 A2 页面骨架 + C2 数据模型 + C3 命令清单 + C4 导入规格 + F1 M0~M7 为骨架；把我们独有的 6 块作为增量并入（C2 加 3 表 + `exam_type`，A2 F2 加解析卡/词卡/空格，D3 加四道守卫）；重写 04 v2.0 / 05 v2.0；原型按 oil-ui 重做 8 页；重生成设计基线（DB 新 ID）。
- **成本**：设计侧约 2~3 个工作轮（重写 04/05 + 8 页原型 + 决策清点）；开发侧 TP1 前端重写（后端 schema 按 C2 调整）。
- **收益**：工程体系（测试/发布/风险/许可/命令契约/导入规格）全部现成，**后面每个包都省事**；且天然满足「多考试 + 多年份 + 用户导入」的扩展。

### 方案 B · 以我方现有设计为主，docs 当参考
- **做法**：保留 04/05 的 4 页 + 9 模块，逐包往 docs 靠；docs 只取 C4 导入细节与 C3 命令命名。
- **成本**：短期最低（TP1 已跑通，直接续 TP2）。
- **风险**：复习/导入/统计/设置/更新**都要在 4 页骨架上硬塞**，等于后面每个包都做一次信息架构改造；且数据模型还得在某个时点补 5 张表 → 迁移两次。**实际上是延迟支付的 A，且更贵。**

### 方案 C · 两套并行（docs 管工程，我方管产品）
- **成本**：看起来省事。
- **风险**：两处都定义数据模型与命令契约，**必然冲突**（现在就有 15 vs 10 表、20+ vs 16 命令）。文档维护约定（索引页 §8）要求「不重复」，并行直接违背。**不推荐。**

### 推荐
**A**。核心理由：冲突的根源不是「谁的文档更好」，而是**产品规模变了**——从「2 页的 CET4 阅读器」变成「8 页的多考试精读工作台 + 用户导入 + 复习」。docs 是按后者写的，我们 04/05 是按前者写的。按 A 重写，等于一次性把规模对齐；按 B 续做，等于用前者的骨架扛后者的功能。
