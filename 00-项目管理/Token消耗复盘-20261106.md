## 二、六个主要消耗源（按估算占比排序）

### 1. 派工 prompt 里「重述」而非「指路」— 约 30~40%

**现象**：我的派工 prompt 普遍 2,000~5,000 字。里面大量是**把 02 任务包的内容抄一遍**（AC 列表、字段口径、D0~D8 改动点、禁止项清单）。

**为什么**：担心子代理不读文件、或读漏，于是「保险起见」抄全。但代价是：56 次 × 平均约 4,000 token ≈ **22 万 token 只花在"下指令"上**，而且抄的内容**每次都要我重新生成一遍**（我也要读 02 才能抄）。

**本会话内的反面证据**：M4 后期的派工 prompt 明显短（只写「必读 3 个文件」+ 关键约束 + 交付格式），子代理照样做对了。第 1 批 D0~D2 只用了 14 分钟、一次过。

**改法**：prompt 只写五要素（目标 / **必读路径** / 本轮新增裁定 / 输出契约 / 停止条件），已有内容一律给路径。预期省 30~40%。

### 2. 证据文档「全量贴输出」— 约 15~20%

**现象**：执行自测 30~64 KB、审查 20~35 KB。里面大量是**命令的完整原始输出**（门禁几百行 PASS 逐条、cargo test 37 个用例逐行列）。

**为什么**：规范要求「真实命令 + 输出片段 + 非空壳自检」，我为了「证据硬」就让它全贴。但贴进去之后：开发员写一遍 → 我读一遍 → 审核员读一遍 → 我再看一遍 = **同一份文本被读 4 次**。

**改法**：**证据分层**——
- 原始日志落 `.tmp/<TP>/*.log`（不进上下文，只在需要时 grep）
- `.md` 里只留：**结论 + 关键断言数字 + 复算命令 + 日志路径**
- 判据「可复算」而不是「已贴出」——审核员要的是能重跑的命令，不是 300 行 PASS 行

预期省 15~20%。

### 3. 多轮审核的重复全量读 — 约 10~15%

**现象**：M4 计划审核 **3 轮**、TP1 **4 轮**。每轮审核员都要重读 02（20 KB）+ 自测（40 KB）+ 代码 diff。

**为什么**：
- 第 1 轮我写错了 5 处（真错，该驳）
- 第 2 轮驳回的是「改 1 处漏 3 处」的**机械残余**（命令数 6→7 只改了一处）
- 第 3 轮才是「5 处 5/5 PASS」

**改法**：
- **数字/签名类改动，改完立刻 grep 计数**（不要靠人眼扫一遍就说改好了）。本会话我在 M4 第 2 轮后才养成这个习惯，一次就过了。
- **审核第 1 轮就要求「同类项全量扫描」**（同一个数字在文档里出现几次、同一个签名出现几次），把机械残余一次清完。

预期省 10~15%，且减少一轮 = 少 1 次完整审核（= 省 1 次 02+自测+diff 的读取）。

### 4. 失败重试 — 约 12%（本会话特有）

**现象**：9 次失败/中断，每次的 prompt 都是几千 token，而且失败前子代理可能**已经读了大量文件**（读进去的 token 白烧）。

时间线：
| 时段 | 故障 | 烧掉的派工 | 真正根因 |
|---|---|---|---|
| 13:21~13:32 | 审核员连续失败 | 3 次 | `scnet` 中转与角色通道不兼容 |
| 18:18~18:41 | 开发员连续失败 | 4 次 | **DeepSeek 官方欠费 -0.03 元** |
| 20:50 | 第 2 批 BLOCKED | 1 次 | **我自己**同时唤醒两个子代理 |

**改法（成本最低、收益最高）**：
- **派工前 5 秒探针**：一条「回一行 OK」的极简派工就能验证通道。我一个探针就定位了欠费问题——但那是试错 45 分钟之后才想到的。
- **余额/额度前置检查**：一次 API `GET /user/balance` 就能提前发现欠费。
- **`send_message` 前先 `list_agents`**：确认没有第二个写入者（这条已写进教训）。

预期省 12% 且少 40 分钟。

### 5. 我反复读同一文件 — 约 8%

**现象**：修文档时「读一段 → 改一处 → 再读一遍确认」的循环。一个小改动能触发 3~4 次文件读取。

**改法**：批量改 + 一次正则校验（我在 M4 v1.2 时做到了：5 处一起改，然后一条命令验证 7 个计数全对）。

### 6. 长会话的上下文压缩 — 隐性但可观

**现象**：15 小时单会话，经历了多次 checkpoint 压缩。每次压缩要把上下文摘要重写，本身消耗 token，且**压缩后保真度下降会引发返工**（我得重新确认状态）。

**改法**：**按包切会话**（M3 一个会话、M4 一个会话），把「跨包连续性」交给磁盘上的 `状态.md` + `决策记录.md`（它们本来就是设计的记忆载体）。代价是新会话要重建少量上下文，但远比反复压缩便宜。

## 三、为什么消耗这么大的结构性原因（不是失误，是设计）

必须说清一点：**这个开销有相当比例是「买可审计性」**，不是浪费。

1. **四角色流水线**：调度员 / 研究员 / 开发员 / 审核员各自要完整读一遍上下文才能工作。这是 4× 的基础成本。
2. **证据优先于简洁**：persona 明确要求「证据/核验/风险优先于简洁，禁止为省 token 压缩证据」。这条保证了「驳回有依据、bug 有根因、决策有留痕」，但也直接推高了文本量。
3. **保守策略**：不确定就查、就验、就重跑。M4 的 AC4 顺延逻辑，我和审核员**各自手算一遍**才发现开发员最初的期望值写错了——这种双人核对很贵，但它挡掉了一个会持续到 M6 的逻辑错误。
4. **双清单纪律**：AI 间通信（派工/状态/台账）不做人读化、人读清单可读性优化——这条是对的，但 AI 间通信的**绝对量**还没压下来。

**所以优化的方向不是「少做审计」，而是「审计的载体更省」**：把原始输出赶进 `.log`，把结论留在 `.md`，把判据交给脚本。

## 四、优化清单（按 ROI 排序）

| # | 措施 | 具体做法 | 预期节省 | 难度 |
|---|---|---|---|---|
| **1** | **派工 prompt 只指路** | 五要素：目标 / 必读路径 / 本轮新裁定 / 输出契约 / 停止条件。**禁止抄 02 的内容** | 30~40% | 低 |
| **2** | **前置通道探针** | 派工前 5 秒一行探针；余额/额度一次 API；`send_message` 前必查 `list_agents` | 12% + 40 分钟 | 极低 |
| **3** | **证据分层** | 原始输出 → `.tmp/*.log`；`.md` 只留结论+关键数字+复算命令+日志路径 | 15~20% | 低 |
| **4** | **机械项脚本化验收** | 数字/签名改动后立刻 grep 计数（不许人眼扫）；同类项全量扫描一次清完 | 10~15% | 低 |
| **5** | **按包切会话** | 一个任务包一个会话，跨包靠 `状态.md`/`决策记录.md` 衔接 | 减少压缩损失 | 中 |
| **6** | **审核抽样 + 反证** | 不全量重跑，只跑关键项 + 要求开发员给可复算命令 + 边界变异测试 | 10~15% | 中 |

## 五、本会话已经验证有效的 4 个改进

不是建议，是做过的：

1. **通道探针**：一个「回一行 OK」的派工，5 分钟内定位了「欠费 vs 插件故障」——之前试错 45 分钟。
2. **正则计数验收**：M4 v1.2 改 5 处后，一条命令验 7 个计数（全 0/全 1），一次通过，省掉一轮审核。
3. **变异测试**：concern 7 的修复让门禁「把 JOIN 改回去看是否变红」——证明了门禁真能抓错，而不是假绿。
4. **证据落 `.tmp`**：M4 的门禁原始日志 43 KB 落 `.log`，`构建记录` 只引关键行——这是对的做法，应该推广到执行自测。

## 六、一个具体的坏例子（供以后避免）

**M3 的派工 prompt**：我把 02 的 D0~D8 八个改动点、AC1~AC9 九条判据、字段口径表、禁止项 10 条全抄进 prompt，约 4,500 字。然后开发员**又去读了 02**（我在「必读」里也让它读了）。

→ 同一份信息，我写一遍、它读两遍（prompt + 文件）。**纯浪费约 6,000 token / 次**。

**对比 M4 第 1 批的 prompt**：只写「本批范围 D0+D1+D2+D7」+ 3 个必读路径 + 4 条本轮新裁定 + 交付格式，约 1,200 字。结果：14 分钟完成、`verify-review 128/128` 一次通过。

**结论：少写 prompt，多给路径，反而更快。**

## 七、建议后续动作（可立即执行）

1. **加一道 `verify:clean` 门禁**：查 NUL / BEL / 孤立 CR / 反斜杠+字母 / 反引号转义残留。本会话这一个坑踩了 **3 次**（5 个文档 NUL、`types.ts` 注释 7 处、脚本内反引号），每次都要单独派工修。
2. **派工模板改造**：把「五要素 + 禁止抄内容」写进预设的派工模板。
3. **余额/额度开机检查**：会话开始查一次 API 余额，欠费直接提示。
4. **`预算台账` 加一列「预计/实际 token」**：等环境挂了计量就能自动回填，否则永远只能靠次数推断。
