# C5 自动更新与发布方案

> 版本：v1.0\
> 状态：定稿\
> 上游文档：`docs/C1-技术方案总览.md`、`docs/C3-Command接口清单.md`\
> 下游文档：`AGENTS.md`、`.github/workflows/publish.yml`、`src-tauri/tauri.conf.json`\
> 本文档定义桌面端（Windows/macOS/Linux）与 Android
> 端的更新机制、签名密钥管理、GitHub Actions 发布流水线和首次验证流程。

------------------------------------------------------------------------

## 1. 一个必须提前说清的事实：桌面和 Android 走两条不同的路

Tauri 官方的 `tauri-plugin-updater` **不支持
Android**。官方平台支持表明确标注：Linux ✓、Windows ✓、macOS
✓、**Android ✗、iOS ✗**。Android
平台出于系统安全策略，**不允许应用自行静默安装
APK**，因此不存在"桌面端那种一键更新并重启"的机制。

这意味着：

  ---------------------------------------------------------------------------------------------------
  平台                          更新方式                                      用户感知
  ----------------------------- --------------------------------------------- -----------------------
  **桌面端**（Win/mac/Linux）   Tauri updater                                 启动时提示或后台完成
                                自动下载、签名校验、静默/被动安装、重启生效   

  **Android**                   应用内检查新版本 → 打开浏览器跳到 GitHub      需要几步手动操作
                                Release 页面 → 用户手动下载 APK → 手动安装    
  ---------------------------------------------------------------------------------------------------

本文档把两条链路分开定义，**不假设 Android 能复用桌面的 updater 逻辑**。

## 2. 桌面端自动更新

### 2.1 机制概述

Tauri updater 的工作方式：应用启动（或手动触发）时，向一个**固定的 URL**
请求 `latest.json`，将其中 `version`
与当前安装版本比较。发现新版本后，下载对应平台的更新包，用**公钥**验证签名，通过则安装并重启。

这个 `latest.json` 由 `tauri-action`
在发布时自动生成，不需要手动维护。端点是
`https://github.com/{owner}/{repo}/releases/latest/download/latest.json`，始终指向最新正式
Release。

### 2.2 签名密钥（不可跳过）

Tauri updater **强制要求签名**，未签名的更新包会被拒绝。密钥对的作用：

- **私钥**：在 CI 构建时对更新包签名。
- **公钥**：嵌入应用，安装前验证签名。

**生成（一次性，在可信机器上）** ：

``` bash
cargo install tauri-cli --version "^2"
cargo tauri signer generate -w ~/.tauri/myapp.key
```

生成后会得到私钥文件（`~/.tauri/myapp.key`）和公钥字符串。公钥填入
`tauri.conf.json` 的 `plugins.updater.pubkey`，私钥写入 GitHub
Repository Secret
`TAURI_SIGNING_PRIVATE_KEY`（完整内容，单行，无换行）。如果生成时设了密码，再加
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。

**私钥丢失 = 永久无法向已安装用户推送自动更新。**
必须离线备份到安全位置，不提交到仓库，不放进 CI 日志。

### 2.3 `tauri.conf.json` 配置

``` json
{
  "bundle": {
    "createUpdaterArtifacts": true
  },
  "plugins": {
    "updater": {
      "active": true,
      "endpoints": [
        "https://github.com/{owner}/{repo}/releases/latest/download/latest.json"
      ],
      "pubkey": "粘贴公钥字符串",
      "windows": {
        "installMode": "passive"
      }
    }
  }
}
```

**`createUpdaterArtifacts: true` 是关键**：没有它，构建时不会生成 `.sig`
签名文件，`latest.json` 无法被正确构造。Windows 的
`installMode: "passive"`
表示静默安装，只显示进度条，不要求用户一路点"下一步"。

### 2.4 `capabilities/default.json` 权限

Tauri v2 的权限模型是显式授权的。不加这一行，前端调用 updater 会被 ACL
拒绝：

``` json
{
  "permissions": [
    "core:default",
    "updater:default"
  ]
}
```

### 2.5 GitHub Actions 工作流

文件放在 `.github/workflows/publish.yml`，触发条件是**推送 `v*`
格式的标签**。

``` yaml
name: publish

on:
  push:
    tags:
      - 'v*'

jobs:
  publish-tauri:
    permissions:
      contents: write
    strategy:
      fail-fast: false
      matrix:
        include:
          - platform: 'windows-latest'
            args: ''
          - platform: 'macos-latest'
            args: '--target universal-apple-darwin'
          - platform: 'ubuntu-22.04'
            args: ''

    runs-on: ${{ matrix.platform }}

    steps:
      - uses: actions/checkout@v4

      - name: Install Linux dependencies
        if: matrix.platform == 'ubuntu-22.04'
        run: |
          sudo apt-get update
          sudo apt-get install -y libwebkit2gtk-4.1-dev libappindicator3-dev \
            librsvg2-dev patchelf

      - uses: actions/setup-node@v4
        with:
          node-version: lts/*

      - uses: dtolnay/rust-toolchain@stable

      - uses: swatinem/rust-cache@v2
        with:
          workspaces: './src-tauri -> target'

      - run: npm ci

      - uses: tauri-apps/tauri-action@v0
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          TAURI_SIGNING_PRIVATE_KEY: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}
          TAURI_SIGNING_PRIVATE_KEY_PASSWORD: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY_PASSWORD }}
        with:
          tagName: v__VERSION__
          releaseName: 'v__VERSION__'
          releaseDraft: false
          prerelease: false
          includeUpdaterJson: true
          args: ${{ matrix.args }}
```

**`includeUpdaterJson: true` 是打通自动更新的开关**。它让 `tauri-action`
汇总各平台的 `.sig` 签名文件，自动生成符合 Tauri updater schema 的
`latest.json`，并作为 Release 附件上传。你不需要手写这个文件。

`macos-latest` 配合 `--target universal-apple-darwin` 产出同时支持 Intel
和 Apple Silicon 的通用包，覆盖 macOS 的两种主流硬件。

**关于 macOS 签名**：上面的工作流**没有配置 Apple
代码签名和公证**。macOS
用户首次打开可能看到"无法验证开发者"的提示，需要手动在系统设置中放行。对于个人开源工具，这是可以接受的取舍；如果以后在意
macOS 体验，再补充 `APPLE_CERTIFICATE`、`APPLE_SIGNING_IDENTITY`
等环境变量，但会产生 Apple Developer 年费。

### 2.6 `latest.json` 的结构（理解用，不需要手动生成）

`latest.json` 的 schema 大致如下，由 `tauri-action` 自动填充 `platforms`
下各平台的 `signature`（来自 `.sig` 文件内容）和 `url`（Release
附件地址）：

``` json
{
  "version": "1.0.1",
  "pub_date": "2026-01-15T10:00:00+00:00",
  "platforms": {
    "windows-x86_64": { "signature": "...", "url": "..." },
    "darwin-aarch64": { "signature": "...", "url": "..." },
    "darwin-x86_64": { "signature": "...", "url": "..." },
    "linux-x86_64": { "signature": "...", "url": "..." }
  }
}
```

**不要手动编辑或上传 `latest.json`**。手动维护的清单一旦与真实 `.sig`
不匹配，签名校验会失败，更新链路静默断裂。

## 3. Android 端更新（手动引导）

### 3.1 为什么不能静默更新

Android 不允许应用自行安装 APK 替换自身。`tauri-plugin-updater` 在
Android 上不可用，这是平台层面的限制，不是配置问题。

因此 Android 端的更新流程是：

1.  应用内**检查**是否有新版本（读取 `latest.json` 或 GitHub Releases
    API）。
2.  如果有，展示版本号和更新说明。
3.  用户点击"下载更新" → **打开系统浏览器**，跳转到 GitHub Release
    页面。
4.  用户手动下载 APK 并安装。

### 3.2 可选实现方式

有两种路径，按对"自动化程度"的要求选择：

**路径 A：用现成的 Android 更新插件（推荐 MVP）**

`tauri-plugin-android-update` 专门填补这个缺口。它的 `check` 命令读取
`latest.json` 比较版本，`download_and_install` 命令**打开浏览器到
Release 页面**，让用户手动下载安装。

接入方式：

``` toml
# src-tauri/Cargo.toml
[dependencies]
tauri-plugin-android-update = "0.2"
tauri-plugin-opener = "2"
```

在移动端注册插件，配置 `owner` 和 `repo`：

``` rust
#[cfg(mobile)]
.plugin(
    tauri_plugin_android_update::Builder::new()
        .owner("你的GitHub用户名")
        .repo("你的仓库名")
        .build()
)
```

`capabilities` 中加 `"android-update:default"` 权限。前端用 `check()` /
`downloadAndInstall()` 调用，行为与桌面端 updater 的 API
风格一致，便于统一 UI 逻辑。

**路径 B：前端直接请求 GitHub Releases API**

不引入插件，前端用 `fetch` 请求
`https://api.github.com/repos/{owner}/{repo}/releases/latest`，比较
`tag_name` 与当前版本，有更新则展示按钮，点击后 `open` 浏览器到 Release
页面。这种方式更轻，但需要处理 GitHub API 的速率限制（未认证 60
次/小时），且没有版本缓存。

**建议**：MVP 用路径 A，插件已经处理了 `latest.json`
解析和版本比较，代码量更少，行为和桌面端对齐。

### 3.3 Android 的版本号约定

`latest.json` 的 `version` 字段同时服务于桌面端和 Android
端。**发布时必须保证 `tauri.conf.json` 的 `version`、`latest.json` 的
`version`、Git Tag 的版本号三者一致**。Android 端检查时比较的是
`latest.json.version`
与安装版本，不一致会导致误判"已是最新"或反复提示更新。

### 3.4 Android APK 的签名

桌面端 updater 的签名密钥**不用于 Android APK 的安装签名**。Android 的
APK 签名是标准的 v2/v3 APK
签名，用于系统验证应用来源的连续性。如果你用同一个密钥库（keystore）签名所有版本的
APK，升级安装时系统会认可；如果更换
keystore，已安装用户将**无法覆盖安装**，必须先卸载。

**MVP 建议**：固定一个 Android keystore，离线备份，与桌面 updater
密钥分开管理。keystore 的密码和别名同样写入 GitHub Secrets。

### 3.5 Android 构建在 GitHub Actions 中的位置

Android 构建需要 Android SDK/NDK 和 Rust 的 Android target。在现有
`publish.yml` 中增加一个 Android job，或在同一 job 中增加 Android
构建步骤。关键点：

- 安装 Android SDK（可用 `android-actions/setup-android`）。
- `rustup target add aarch64-linux-android` 等。
- 配置 keystore 签名（通过 `TAURI_SIGNING_PRIVATE_KEY`
  之外的环境变量传入 Android keystore）。
- 产物 `.apk` 上传到同一个 Release。

Android 构建链路的细节（NDK 版本、Gradle 配置）超出本文档范围，按 Tauri
v2 移动端构建官方文档执行，**MVP 阶段先确保桌面端链路稳定，Android
构建作为第二个里程碑**。

## 4. 发布流程（桌面 + Android 统一）

### 4.1 版本号约定

版本号遵循 `MAJOR.MINOR.PATCH`。每次发布：

1.  修改 `src-tauri/tauri.conf.json` 的 `version`。
2.  修改 `src-tauri/Cargo.toml` 的 `version`（保持一致）。
3.  提交，推送。
4.  打标签并推送：`git tag v1.0.1 && git push origin v1.0.1`。

`tauri-action` 会用这个标签创建 Release，`latest.json` 的 `version` 来自
`tauri.conf.json`，因此**版本号必须在打标签前改好**。

### 4.2 Actions 自动执行的内容

推送标签后，`publish.yml` 自动完成：

1.  三平台（Win/mac/Linux）矩阵构建。
2.  用私钥签名更新包，生成 `.sig`。
3.  创建 GitHub Release。
4.  上传各平台安装包、`.sig`、`latest.json`。
5.  如果配置了 Android job，同时上传 APK。

**公开仓库的 GitHub Actions 标准运行器免费**，这条链路的现金成本为 0。

### 4.3 首次发布验证（不可跳过）

**这一步是整条链路唯一不能靠 CI 绿灯替代的验证。**

1.  先发布 `v1.0.0`，在本地安装桌面版。
2.  把版本号改为 `1.0.1`，发布 `v1.0.1`。
3.  重新打开已安装的 `v1.0.0`，确认它能**检测到
    `1.0.1`、下载、签名校验通过、完成安装并重启**。
4.  检查 `latest.json` 是否包含当前平台的 `signature` 和 `url`，且 `url`
    可访问。
5.  Android 端：安装 `v1.0.0` APK，确认检查到 `1.0.1`
    时能正确跳转浏览器。

**如果首次验证失败，不要继续发版**。常见原因：公钥/私钥不匹配、`createUpdaterArtifacts`
未开启、`latest.json` 未上传、endpoint 路径写错、`capabilities` 缺
`updater:default`。

## 5. 密钥与 Secret 汇总

  ---------------------------------------------------------------------------------------------
  Secret / 配置                          用途                     存储位置
  -------------------------------------- ------------------------ -----------------------------
  `TAURI_SIGNING_PRIVATE_KEY`            桌面端 updater           GitHub Repository Secret
                                         私钥，签名更新包         

  `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`   私钥密码（如果设置了）   GitHub Repository Secret

  `plugins.updater.pubkey`               桌面端 updater 公钥      `tauri.conf.json`（可公开）

  Android keystore 及密码                Android APK 签名         GitHub Secrets + 离线备份
  ---------------------------------------------------------------------------------------------

**私钥和 keystore 都不能提交到仓库。**
一旦泄露，立即视为已失效，但轮换桌面端 updater
密钥意味着**已安装用户永久无法自动更新**，只能手动重装。因此桌面端
updater 私钥的保管优先级高于一切其他凭据。

## 6. `check_update` command（对接 C3）

C3 中定义了 `check_update` 命令，本文档明确其实现策略：

- **桌面端**：调用 `tauri-plugin-updater` 的 `check()`，返回
  `available / current_version / latest_version / notes / download_url`。
- **Android 端**：调用 `tauri-plugin-android-update` 的
  `check()`，返回结构对齐，`download_url` 指向 Release 页面而非直接 APK
  文件。
- **失败处理**：网络错误返回 `network_error`，更新器内部错误返回
  `updater_error`。**检查更新失败不阻塞应用使用**，前端仅 toast 提示。

## 7. 故障处理与回滚

  -------------------------------------------------------------------------------------
  场景                                处理
  ----------------------------------- -------------------------------------------------
  新版本有严重 bug，需要撤回          **不要删除 Release 或修改
                                      `latest.json`**。发布一个更高版本号的修复版（如
                                      `1.0.2`），让 updater 自然指向新版本。删除
                                      Release 会导致已下载的用户更新链断裂，且
                                      `releases/latest/download/latest.json` 可能 404。

  签名校验失败                        检查公钥是否与私钥匹配；检查 `latest.json` 中
                                      `signature` 是否为对应 `.sig` 文件内容；检查
                                      `createUpdaterArtifacts` 是否为 `true`。

  `latest.json` 404                   确认 Release 不是 draft，且
                                      `includeUpdaterJson: true` 已生效；确认 endpoint
                                      路径中的 `{owner}/{repo}` 正确。

  Android 无法覆盖安装                检查新 APK 是否用**同一 keystore** 签名；检查
                                      `versionCode` 是否递增。

  macOS 用户无法打开                  MVP 未签名/公证，用户需在"系统设置 →
                                      隐私与安全性"中手动放行。
  -------------------------------------------------------------------------------------
