## 1. 文档说明

### 1.1 目的

回答三个问题：

1.  **有哪些风险**：按类别汇总，不遗漏关键项。
2.  **每条风险多严重**：分级、触发条件、影响范围。
3.  **怎么应对**：预防措施、发生后的处理、监控方式。

### 1.2 范围

覆盖从开发到发布后维护的全生命周期。风险来源包括 A1 第 9 节、F1
各里程碑风险、F3 各 ADR 的"后果"章节、E2
的责任边界分析。**不重复**技术实现细节，只列风险与应对。

### 1.3 维护规则

- 新风险追加，已发生或已消除的风险标注状态，不删除。
- 风险等级变化需在 `docs/F3-决策记录.md` 中留痕。
- 每个里程碑结束时回顾一次本文档，确认应对措施是否落地。

## 4. 法律与合规风险

### R01 内置文章未经授权分发

**等级**：P0 ｜ **状态**：⚠️ 已接受

**触发条件**：内置文章的权利人发现项目并主张权利，或 GitHub 收到投诉。

**影响**： - 最坏：收到律师函或起诉，面临索赔。 -
常见：收到下架通知，被迫移除内置内容。 - 项目声誉受损。

**为什么定为 P0**：这是项目唯一的"可能直接导致法律追责"的风险，且路径 B
下无法用免责声明化解。

**应对措施**： - **已接受**：项目决定承担此风险（路径 B），不写
E3，不声称授权。 - **降低触发概率**：README 和 DISCLAIMER
不写"已获授权"，不写"如有侵权请联系删除"；内置内容定位为"演示性质"，不做内容库更新、推荐、分享。 -
**降低影响**：内置内容与代码结构分离（`src-tauri/resources/seed/`），一旦需要移除，可以快速发布不含内置文章的版本，用户数据不受影响。 -
**预案**：收到通知后，立即移除内置内容，发布补丁版本，在 Release Notes
中说明。

**监控方式**：关注 GitHub
Issues、仓库通知邮箱；定期检查内置内容是否有可替代的自编方案。

**相关文档**：E2 第 4.4 节、F3 ADR-015

------------------------------------------------------------------------

### R02 用户导入内容引发版权纠纷

**等级**：P1 ｜ **状态**：🟡 处理中

**触发条件**：用户导入侵权内容，权利人追究，且追溯到工具提供方。

**影响**：项目被要求配合调查或承担责任。

**应对措施**： - 产品不存储、不传播、不审核用户内容（E2 第 4.1 节）。 -
导入页面有 UGC 合法性提示（E2 第 4.3 节，A2 F5 需落地）。 - README 和
DISCLAIMER 明确责任边界。 -
不做分享、公开、社区功能，避免从"工具"变成"平台"。

**监控方式**：确认 M5 导入页提示已实现；确认没有新增分享功能。

**相关文档**：E2 第 4.1---4.3 节

------------------------------------------------------------------------

### R03 免责声明被认定为无效

**等级**：P1 ｜ **状态**：🟡 处理中

**触发条件**：纠纷中，法院或对方主张免责声明不能免除法定责任。

**影响**：免责声明无法起到预期保护作用。

**说明**：免责声明能覆盖"工具按现状提供"和"用户导入内容自负其责"，但**不能覆盖"平台自己分发未经授权内容"**（R01）。这是路径
B 的已知局限。

**应对措施**： - 免责声明措辞保守，不自认侵权，不虚假声称授权（E2 v1.1
已调整）。 - 不依赖免责声明化解 R01，R01 单独作为已接受风险处理。 -
涉及具体纠纷时咨询律师，不把 DISCLAIMER 当法律意见书。

**监控方式**：发布前确认 DISCLAIMER 与 E2 一致。

**相关文档**：E2 第 3.2 节、第 4.4 节

------------------------------------------------------------------------

### R04 引入 GPL/AGPL 依赖导致许可冲突

**等级**：P1 ｜ **状态**：⬜ 未处理

**触发条件**：引入具有强 copyleft 效应的依赖（GPL、AGPL）。

**影响**：MIT 项目被迫以 GPL 发布，与定位冲突；或被迫移除依赖，返工。

**应对措施**： - 引入新依赖前检查许可证，拒绝 copyleft 类（E2 第 5.3
节）。 - 发布前用 `cargo-license`、`license-checker` 扫描。 -
`THIRD_PARTY_NOTICES.md` 记录直接依赖许可证。

**监控方式**：CI 中加入许可证扫描（P1，可在 M7
前加）；每次新增依赖时人工确认。

**相关文档**：E2 第 5 节

## 5. 内容与数据风险

### R05 笔记数据丢失或损坏

**等级**：P0 ｜ **状态**：🟡 处理中

**触发条件**： - 应用更新后数据库被重置（IndexedDB 类问题，已通过 SQLite
规避）。 - 保存失败但本地草稿未保留。 - 用户误删或设备故障。

**影响**：用户笔记、生词、复习记录丢失，核心价值受损，用户流失。

**为什么定为
P0**：笔记是产品的核心资产，丢失不可逆，且直接违背"本地优先"的承诺。

**应对措施**： - 使用 SQLite 而非 IndexedDB（F3 ADR-006）。 -
笔记自动保存 + 本地草稿兜底（D1 第 8.3 节）。 -
保存失败不丢输入，展示重试（A2 F2.5）。 - 提供导出功能作为备份手段（A2
F3.5、F7.1）。 - 数据备份/恢复（P1，M6）。

**监控方式**：D3 测试覆盖"重启后笔记不丢""保存失败输入不丢"；M7
发布前验证"更新后数据不丢"。

**相关文档**：F3 ADR-006、D1 第 8.3 节、A2 F2.5

------------------------------------------------------------------------

### R06 SQLite 数据库文件损坏

**等级**：P1 ｜ **状态**：⬜ 未处理

**触发条件**：磁盘故障、应用异常退出时正在写入、文件被外部程序修改。

**影响**：应用无法读取数据，用户笔记全部不可用。

**应对措施**： - 写操作使用事务，异常时回滚（D1 第 3 节）。 -
启动时检测数据库完整性（`PRAGMA integrity_check`，P1）。 -
提供数据备份/恢复功能（A2 F7.1）。 -
损坏时提示用户从备份恢复，不静默失败。

**监控方式**：M6 实现备份功能后验证恢复流程；启动检测加入 D3 测试。

**相关文档**：D1 第 5 节、A2 F7.1

------------------------------------------------------------------------

### R07 导入切句/偏移错误导致笔记错位

**等级**：P1 ｜ **状态**：🟡 处理中

**触发条件**：切句规则覆盖不到某种文本，或 UTF-16 偏移计算错误。

**影响**：用户点 A 句弹出 B 句，笔记写到错误位置，精读体验崩坏。

**应对措施**： - C4 第 12
节完整测试用例（缩写、小数、引号、省略号、中文、emoji）。 -
`utf16_slice` 单独测试，覆盖代理对。 - commit 时 L3 覆盖校验，`surface`
与文本不一致返回错误。 - 预览页只读，用户确认后入库；切句异常有
warning。

**监控方式**：D3 第 3.2---3.4 节测试全绿；M5
手动用真实文章验证点击定位。

**相关文档**：C4 第 6、7、8、12 节

------------------------------------------------------------------------

### R08 种子偏移量错误导致点击串位

**等级**：P1 ｜ **状态**：⬜ 未处理

**触发条件**：24 篇内置文章的 JSON 中 `start_offset` / `end_offset`
与文本不一致。

**影响**：内置文章精读时点击串位，与 R07
表现相同，但根源在种子数据而非解析代码。

**应对措施**： - M1 入库前写测试校验种子偏移（D3 第 7.1 节）。 -
种子导入走与 `commit_import` 相同的 L3 覆盖校验。 -
单篇失败不阻塞其他篇，记录错误日志。

**监控方式**：M1 结束时手动点击验证至少 3 篇；种子校验测试加入 CI。

**相关文档**：C2 第 7 节、D3 第 7.1 节、F1 M1 风险

## 6. 技术与跨平台风险

### R09 自动更新签名密钥丢失

**等级**：P0 ｜ **状态**：🟡 处理中

**触发条件**：私钥文件丢失、损坏，或 GitHub Secret 被删除。

**影响**：**已安装用户永久无法通过自动更新升级**，只能手动重装。这是不可逆的。

**为什么定为 P0**：不可逆，且影响所有已安装用户。

**应对措施**： - 私钥离线备份到安全位置，不提交仓库（C5 第 2.2 节）。 -
备份至少两份，存放于不同位置。 - GitHub Secret 配置后不随意修改。 -
首次发布前实际验证更新链路（C5 第 4.3 节）。

**监控方式**：发布前确认备份存在；密钥轮换时走 F3 决策记录。

**相关文档**：C5 第 2.2、5 节，D1 第 10.3 节

------------------------------------------------------------------------

### R10 自动更新链路断裂

**等级**：P1 ｜ **状态**：⬜ 未处理

**触发条件**：公钥/私钥不匹配、`createUpdaterArtifacts`
未开、`latest.json` 未上传、endpoint 写错、`capabilities` 缺权限。

**影响**：用户收不到更新，停留在旧版本，可能错过安全修复。

**应对措施**： - C5 第 7 节故障排查清单。 - 首次发布必须实际验证（C5 第
4.3 节）。 - 每次发版后检查 `latest.json` 的 `signature` 和 `url`。 -
不删除 Release、不手改 `latest.json`（D1 第 11 节红线）。

**监控方式**：每次发版后手动检查 Release
附件；至少一次完整的"旧版本→新版本"验证。

**相关文档**：C5 第 4、7 节，D1 第 10 节

------------------------------------------------------------------------

### R11 GitHub 访问不稳定

**等级**：P1 ｜ **状态**：⚠️ 已接受

**触发条件**：国内网络环境访问 GitHub 受限。

**影响**：用户下载安装包、检查更新失败；开发者 CI 偶发失败。

**应对措施**： - **已接受**：项目定位为开源工具，用户需自备网络条件。 -
README 说明下载来源，不承诺镜像。 - 更新检查失败不阻塞应用使用（C3 5.10
节）。 - 未来可选：同步到其他代码托管平台作为镜像（P2）。

**监控方式**：关注 Issue 中关于下载失败的反馈。

**相关文档**：F3 ADR-003、C5 第 6 节

------------------------------------------------------------------------

### R12 Android APK 签名变更导致无法覆盖安装

**等级**：P1 ｜ **状态**：⬜ 未处理

**触发条件**：更换 Android keystore，或用不同 keystore 签名新版本。

**影响**：已安装用户无法覆盖安装新版本，必须先卸载，**卸载会丢失本地数据**。

**应对措施**： - 固定一个 Android keystore，离线备份（C5 第 3.4 节）。 -
keystore 密码和别名写入 GitHub Secrets。 - 与桌面 updater
密钥分开管理，不混用。 - README 和 Release Notes 说明升级需同一签名。

**监控方式**：首次 Android 发版后，验证 v1.0.0 → v1.0.1 覆盖安装成功。

**相关文档**：C5 第 3.4 节、D1 第 10.2 节

------------------------------------------------------------------------

### R13 跨平台 WebView 差异

**等级**：P1 ｜ **状态**：🟡 处理中

**触发条件**：Windows WebView2、macOS WKWebView、Linux WebKitGTK 对
CSS、滚动、事件处理行为不一致。

**影响**：精读页点击定位、面板弹出、长列表滚动在某平台异常。

**应对措施**： - 核心交互在 Windows/macOS/Android 手动验证（D3 第 6
节）。 - 避免依赖平台特有 API。 - CSS 使用保守写法，不追新特性。 -
发现问题记录平台和版本，优先修复影响点击定位的问题。

**监控方式**：每个里程碑结束时在至少两个平台走查核心交互。

**相关文档**：D3 第 6 节、F1 各里程碑风险

------------------------------------------------------------------------

### R14 Tauri v2 Android 成熟度不足

**等级**：P2 ｜ **状态**：🟡 处理中

**触发条件**：Tauri v2 的 Android 构建或运行时出现未预期问题。

**影响**：Android 版本延期或体验不佳。

**应对措施**： - Android 作为 M7 之后的可选任务，不阻塞桌面首发（F1 第
11 节）。 - 早期在真机验证构建和运行。 - 保留"纯桌面首发"的降级方案。

**监控方式**：M7 阶段在真机验证；关注 Tauri 社区 Android 相关 Issue。

**相关文档**：C1 第 11 节、F1 M7

------------------------------------------------------------------------

### R15 Rust 侧 AI 生成代码质量不可控

**等级**：P1 ｜ **状态**：🟡 处理中

**触发条件**：Vibe Coding 生成 Rust 代码时，所有权、生命周期、`Mutex`
作用域、`stmt` drop 时机等出错。

**影响**：编译失败、运行时 panic、事务未提交或未回滚。

**应对措施**： - D1 第 12 节提示词模板明确约束。 -
关键逻辑（事务、`utf16_slice`、复习推进）先写测试再实现。 - Rust
侧手写比例适当提高，不全部依赖 AI。 - 编译错误完整贴回 AI 迭代。

**监控方式**：`cargo test` 全绿；事务回滚测试通过；代码评审关注 `stmt`
drop 和 `tx.commit()`。

**相关文档**：D1 第 12 节、C4 第 9 节

## 7. 发布与分发风险

### R16 冷启动体验空，用户不知道怎么用

**等级**：P1 ｜ **状态**：🟡 处理中

**触发条件**：用户打开应用，看到文章但不知道"点句子写笔记"是核心用法；或只做导入工具时文章库为空。

**影响**：首次使用流失，留存低。

**应对措施**： - 首次启动 3 步引导（A2 F8）。 -
精读页首次点击提示气泡。 - 内置文章作为冷启动内容（但受 R01 约束）。 -
示例笔记（P1）。

**监控方式**：M6 验收首次引导；收集用户反馈。

**相关文档**：A2 F8、F3 ADR-011

------------------------------------------------------------------------

### R22 版本号不一致导致更新误判

**等级**：P1 ｜ **状态**：⬜ 未处理

**触发条件**：`tauri.conf.json`、`Cargo.toml`、Git Tag、`latest.json`
的版本号不一致。

**影响**：桌面端反复提示更新或检测不到更新；Android 端误判"已是最新"。

**应对措施**： - 发布前检查版本号三处一致（C5 第 4.1 节、D1 第 10.3
节）。 - `tauri-action` 用 `tauri.conf.json` 的版本生成
`latest.json`，打标签前改好版本号。 - 发布检查清单中加入此项（F1 第 12
节）。

**监控方式**：每次发版后检查 `latest.json` 的 `version` 与 Tag 一致。

**相关文档**：C5 第 3.3、4.1 节

## 8. 产品与用户风险

### R17 笔记依赖用户主动性，留存低

**等级**：P1 ｜ **状态**：⬜ 未处理

**触发条件**：用户不愿意写笔记，觉得"点开是空白输入框"没价值。

**影响**：核心闭环不成立，用户用完一次就流失。

**应对措施**： - 降低记录门槛：面板字段少、自动保存、无格式要求（A2
F2.5、F2.6）。 - 引导和示例（A2 F8）。 -
复习机制让笔记"有用"，形成正反馈（A2 F4）。 -
观察指标：句子点击率、单词收藏率（A1 第 6 节）。

**监控方式**：内测阶段收集用户行为反馈；观察"精读完成率"和"篇目复习完成率"。

**相关文档**：A1 第 6 节、F3 ADR-011

------------------------------------------------------------------------

### R18 差异化弱，被替代品覆盖

**等级**：P2 ｜ **状态**：⬜ 未处理

**触发条件**：通用笔记工具或背单词 App 增加类似功能。

**影响**：用户选择替代品，项目增长停滞。

**应对措施**： - 聚焦"四级精读 + 篇级复习"的组合，不做大而全。 -
保持本地优先、零成本、开源透明的差异化。 -
不在功能数量上竞争，在"点句点词 + 复习提醒"的顺滑度上竞争。

**监控方式**：关注同类工具动态；收集用户"为什么用这个而不用 XX"的反馈。

**相关文档**：A1 第 2.3 节

------------------------------------------------------------------------

## 9. 维护与可持续风险

### R19 个人维护精力不足

**等级**：P1 ｜ **状态**：🟡 处理中

**触发条件**：Issue 堆积、更新停滞、生活工作挤占时间。

**影响**：项目进入"半维护"状态，用户信任下降。

**应对措施**： - README 和 DISCLAIMER 明确"尽力而为、无支持义务"（E2 第
5 节）。 - Issue 模板引导用户提供完整信息，减少无效沟通。 -
不承诺响应时间和路线图。 -
文档齐全，降低未来的维护成本（本文档体系本身就是应对措施）。

**监控方式**：定期回顾 Issue 积压；必要时在 README 标注维护状态。

**相关文档**：E2 第 5 节、F3 ADR-017

------------------------------------------------------------------------

### R20 依赖库安全漏洞无跟进

**等级**：P1 ｜ **状态**：⬜ 未处理

**触发条件**：Tauri、React、rusqlite
等依赖爆出安全漏洞，项目未及时升级。

**影响**：用户面临安全风险，项目声誉受损。

**应对措施**： - 启用 GitHub Dependabot 自动提醒（P1，M7 前配置）。 -
关注依赖的 Release Notes。 - 升级前跑全量测试（D3）。 -
安全漏洞修复优先于功能开发。

**监控方式**：Dependabot 告警；每月检查一次依赖更新。

**相关文档**：D1 第 3 节版本锁定规则

------------------------------------------------------------------------

### R21 项目停止维护后用户数据不可用

**等级**：P2 ｜ **状态**：🟡 处理中

**触发条件**：项目归档或停止，用户仍想使用已有数据。

**影响**：用户笔记被锁定在旧应用中。

**应对措施**： - 本地优先架构：数据在用户设备上，不依赖服务端（F3
ADR-002、ADR-006）。 - SQLite 是标准格式，可用其他工具打开。 -
导出功能（A2 F3.5）提供额外备份。 - 开源代码允许用户自行构建或 fork（F3
ADR-003）。

**监控方式**：确保导出功能可用；README 说明数据位置和格式。

**相关文档**：F3 ADR-002、ADR-003、ADR-006

## 11. 风险监控与复盘机制

### 11.1 每个里程碑结束时

- 回顾本文档，确认该阶段相关风险的应对措施是否落地。
- 新增风险追加到第 3 节总览表。
- 状态变化更新（⬜ → 🟡 → ✅ 或 ⚠️）。

### 11.2 发布前

- 逐项检查 P0、P1 风险的应对措施是否完成。
- 确认 R01 的"已接受"状态在 README 和 DISCLAIMER 中有对应表述。
- F1 第 12 节发布前检查清单与本文档交叉核对。

### 11.3 发布后

- 关注 Issue 中与风险相关的反馈（下载失败、数据丢失、更新异常）。
- 每月检查一次依赖安全（R20）和 GitHub 通知（R01）。
- 风险实际发生时，记录到 F3 决策记录，说明处理过程。
