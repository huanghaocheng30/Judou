# F3 决策记录（ADR）

> 版本：v1.0\
> 状态：持续更新\
> 上游文档：`docs/A1-项目定义卡.md`、`docs/C1-技术方案总览.md`\
> 下游文档：所有 `docs/` 文档的变更需引用本文档编号\
> 本文档记录项目的关键架构与产品决策，说明背景、备选方案、理由和后果。目的是让三个月后的自己和未来的贡献者知道"为什么这么选"，而不只是"选了什么"。

## 1. 文档说明

### 1.1 目的

回答一个问题：**为什么是现在这个方案，而不是当时考虑过的其他方案？**

技术方案文档（C1---C5）写的是"是什么、怎么做"，本文档写的是"为什么"。当有人质疑某个选型、或想改回某个备选方案时，先读这里。

### 1.2 格式

每条决策（ADR）包含：

  字段       说明
  ---------- -----------------------------------------
  编号       `ADR-XXX`，按主题分组，不复用
  标题       一句话描述决策
  状态       `已采纳` / `已替代` / `已废弃` / `待定`
  背景       当时面临什么问题
  决策       最终选了什么
  备选方案   当时考虑过但没选的方案
  理由       为什么选这个
  后果       这个决策带来什么约束和代价
  相关文档   哪些文档受此决策影响

### 1.3 维护规则

- 新决策追加，不修改已采纳的 ADR 正文。
- 决策被推翻时，旧 ADR 状态改为 `已替代`，新增一条 ADR 说明替代原因。
- 所有 `docs/` 文档的关键取舍变更，必须引用对应 ADR 编号。

## 3. 分发与形态

### ADR-001 放弃微信小程序，走桌面 + APK + GitHub 分发

**状态**：已采纳

**背景**：最初考虑用微信小程序承载产品，因为用户"即用即走"、获客路径短。但小程序审核对"用户生成内容"的类目有明确限制：涉及用户自行生成笔记记录、分享的小程序，属于"社交-笔记"范畴，**个人主体小程序未开放该类目**。产品的核心功能是用户写句笔记、词笔记、导入文章，恰好踩在这条线上。

**决策**：放弃微信小程序，改为 Tauri 桌面应用（Windows/macOS/Linux）+
Android APK，通过 GitHub Releases 分发。

**备选方案**：

  --------------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- --------------------------------------------
  个人主体小程序 + 砍掉笔记功能       砍掉笔记后产品不再是精读工具，失去核心价值

  注册企业主体继续做小程序            需要营业执照、认证费、ICP
                                      备案，个人项目成本过高

  只做 H5 网页                        需要服务器托管，与"零现金成本"目标冲突
  --------------------------------------------------------------------------------

**理由**：

1.  笔记是产品核心，不能砍。
2.  桌面 + APK 的分发权在自己手里，不依赖平台审核。
3.  GitHub Releases 零成本，符合个人开源项目的成本约束。

**后果**：

- 失去微信生态的获客便利，冷启动更难。
- 需要自己处理跨平台构建、安装、更新。
- 产品形态从"轻量小程序"变成"需要下载安装的桌面/移动应用"，用户门槛变高。

**相关文档**：A1 第 8 节、C1 第 2 节、C5、F1 M7

### ADR-002 不做在线 Web 服务，桌面安装包承载 Web 能力

**状态**：已采纳

**背景**：Web 版本需要服务器托管前端、可能需要后端 API
和数据库，产生持续费用。项目的现金成本目标是接近零。

**决策**：不提供在线 Web 服务。前端的 H5 能力通过 Tauri
封装进桌面安装包，用户下载后在本地运行，数据存本地。

**备选方案**：

  ----------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- ----------------------------------------
  静态前端托管在 GitHub Pages /       只能解决前端托管，后端 API
  Vercel                              和数据库仍需服务

  用 Serverless 函数做后端            有免费额度，但引入运维复杂度和潜在费用

  纯前端 + 浏览器本地存储             IndexedDB 存在更新后数据重置风险（见
                                      ADR-006）
  ----------------------------------------------------------------------------

**理由**：

1.  桌面安装包 = 前端 + 本地数据库，不需要服务器。
2.  数据本地化，隐私更好，无后端成本。
3.  Tauri 的 WebView 能完整运行 React 前端，体验接近 Web。

**后果**：

- 用户不能"打开链接就用"，必须下载安装。
- 跨平台 WebView 差异需要手动验证（见 D3 第 3 节）。
- 未来若要做真正的在线协作或多设备同步，需要重新引入服务端。

**相关文档**：A1 第 7.2 节、C1 第 3 节、C5

### ADR-003 开源 + GitHub Releases 分发，不上应用商店

**状态**：已采纳

**背景**：国内安卓应用商店对个人开发者上架有软著、APP 备案等要求；Google
Play 对个人开发者有 20 人 14
天封闭测试门槛。应用商店的审核周期和资质成本与个人开源项目的节奏不匹配。

**决策**：代码在 GitHub 开源，安装包通过 GitHub Releases
分发，自动更新走 Tauri updater + 静态 `latest.json`。不上任何应用商店。

**备选方案**：

  方案             为什么没选
  ---------------- ----------------------------------------------------
  上国内安卓商店   个人主体需软著（30---60 工作日）+ APP 备案，成本高
  上 Google Play   个人开发者需 20 人 14 天封闭测试，冷启动门槛高
  只做官网下载     需要域名和托管，GitHub Releases 已足够

**理由**：

1.  GitHub Releases 零成本、版本可追溯、可附校验和。
2.  公开仓库的 GitHub Actions 免费，构建成本为零。
3.  开源与"个人维护、尽力响应"的定位一致。

**后果**：

- 用户需要信任 GitHub 下载来源，部分用户会犹豫。
- 国内访问 GitHub 可能不稳定，需要用户自备网络条件。
- 无法触达应用商店的自然流量。

**相关文档**：A1 第 8 节、C1 第 8 节、C5 第 2 节

## 4. 技术栈

### ADR-004 Tauri v2 而非 Electron

**状态**：已采纳

**背景**：需要把 React 前端封装成桌面应用。Electron 和 Tauri
是两条主流路线。

**决策**：使用 Tauri v2。

**备选方案**：

  -----------------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- -----------------------------------------------
  Electron                            安装包 80---150MB，空闲内存
                                      150---300MB，对个人项目的分发和用户体验不友好

  纯 Web + PWA                        无法直接操作本地 SQLite，数据持久化不可靠
  -----------------------------------------------------------------------------------

**理由**：

1.  **安装包小一个数量级**：Tauri 通常 2.5---10MB，用户下载快，GitHub
    Releases 带宽压力小。
2.  **内存占用低**：空闲 30---40MB，老旧电脑也能跑。
3.  **Rust 后端直接操作 SQLite**：不需要 Node 侧车进程，架构更简单。
4.  **官方支持 GitHub Actions 构建**：与分发链路天然衔接。

**后果**：

- Rust 学习曲线比 Node 陡，Vibe Coding 时 Rust 侧需要更多人工介入。
- 跨平台 WebView 差异（Windows WebView2、macOS WKWebView、Linux
  WebKitGTK）需要手动验证。
- 生态比 Electron 小，遇到问题可参考的社区方案少。

**相关文档**：C1 第 2 节、D2 第 2 节

------------------------------------------------------------------------

### ADR-005 React + Vite + TypeScript，放弃 Taro/uni-app

**状态**：已采纳

**背景**：项目最初考虑过微信小程序，因此评估过 Taro（React 语法）和
uni-app（Vue 语法）。ADR-001 放弃小程序后，Taro 的多端编译价值不再需要。

**决策**：直接使用 React 18 + Vite + TypeScript 独立项目，由 Tauri
承载桌面和 Android。不使用 Taro、uni-app 或任何小程序框架。

**备选方案**：

  ----------------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- ----------------------------------------------
  Taro                                核心价值是小程序多端编译，小程序已放弃，Taro
                                      只增加编译层和调试复杂度

  uni-app                             同上；且 Vue 对 AI 编码的友好度略低于 React

  原生 Android + 原生桌面             需要维护两套 UI 代码，Vibe Coding 成本翻倍
  ----------------------------------------------------------------------------------

**理由**：

1.  **React 对 AI 编码更友好**：AI 训练数据中 React
    占比高，生成的代码质量更稳定。
2.  **TypeScript 约束**：类型系统能拦住 AI
    生成的部分错误，减少运行时崩溃。
3.  **减少一层编译**：没有 Taro 的编译产物和适配层，调试链路更短。
4.  **Tauri 官方模板就是 React + Vite**：配置路径最短。

**后果**：

- 如果未来重新需要小程序，需要另起一套代码或重新评估 Taro。
- 前端依赖版本需要自己维护，不享受 Taro/uni-app 的集成封装。

**相关文档**：C1 第 2.1 节、D1 第 3 节、D2 第 4.4 节

### ADR-006 SQLite（rusqlite）而非 IndexedDB 或其他

**状态**：已采纳

**背景**：本地优先应用需要持久化用户笔记、生词、复习计划。候选方案包括
IndexedDB（WebView 内置）、SQLite（rusqlite）、文件存储（JSON）。

**决策**：使用 SQLite，通过 rusqlite 访问，数据库文件存在
`app_data_dir/app.db`。

**备选方案**：

  ----------------------------------------------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- ----------------------------------------------------------------------------
  IndexedDB                           **Tauri 的 WebView 中 IndexedDB
                                      不会跨应用更新持久化**，用户安装新版本后数据可能重置，对笔记类应用不可接受

  JSON 文件                           无事务、无索引、并发写不安全，数据量增大后查询慢

  远程数据库                          有服务器成本，与 ADR-002 冲突
  ----------------------------------------------------------------------------------------------------------------

**理由**：

1.  **持久化可靠**：SQLite 是文件，应用更新不重置。
2.  **事务支持**：导入、复习推进等写操作需要原子性。
3.  **索引和查询能力**：生词筛选、复习到期查询、统计都需要 SQL。
4.  **rusqlite `bundled` feature**：SQLite
    编译进二进制，用户机器不需要预装。

**后果**：

- 需要自己管理 migration，不能像 IndexedDB 那样"随手加字段"。
- 数据库文件损坏时需要备份恢复机制（A2 F7.1，P1）。
- 前端不能直接访问，所有读写必须经 Tauri command。

**相关文档**：C1 第 2、7 节、C2、D1 第 5 节

------------------------------------------------------------------------

### ADR-007 rusqlite 手写 SQL，不用 ORM、不用连接池

**状态**：已采纳

**背景**：数据层需要选择数据访问方式。候选包括
ORM（Diesel、SeaORM）、Query Builder（sqlx）、手写 SQL（rusqlite）。

**决策**：使用 rusqlite 手写 SQL，连接用 `State<Mutex<Connection>>`
管理，单连接，不开连接池。

**备选方案**：

  --------------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- --------------------------------------------
  Diesel / SeaORM                     表结构简单，ORM
                                      的抽象和编译期检查带来的收益低于学习成本和
                                      AI 生成歧义

  sqlx                                异步、需要数据库连接串，与桌面单文件 SQLite
                                      场景不完全匹配

  连接池（r2d2 等）                   单用户桌面场景，并发极低，连接池是过度设计
  --------------------------------------------------------------------------------

**理由**：

1.  **表结构简单**：15 张表，查询以单表或简单 join 为主，手写 SQL 可控。
2.  **事务边界清晰**：手写 SQL 更容易控制"校验在事务外、写入在事务内"。
3.  **AI 生成歧义少**：给 AI 明确"rusqlite + 手写 SQL + Mutex"，比让它选
    ORM 更不容易跑偏。
4.  **单连接足够**：桌面单用户，SQLite 写操作短事务，Mutex 足够。

**后果**：

- SQL 需要自己写和维护，没有 ORM 的自动迁移。
- 复杂查询需要手写 join，容易出错，需要测试覆盖。
- 如果未来引入多窗口并发写，可能需要重新评估连接策略。

**相关文档**：C1 第 2 节、C2 第 5 节、D1 第 5.1 节

## 5. 数据

### ADR-008 偏移量统一 UTF-16 code unit

**状态**：已采纳

**背景**：精读页需要精确点击句子和单词，前端渲染高亮依赖文本偏移量。Rust
和 JavaScript 的字符串索引单位不同：Rust 的 `len()`
是字节，`chars().count()` 是 Unicode 标量；JavaScript 的字符串索引是
UTF-16 code unit。

**决策**：所有 `start_offset` / `end_offset` 统一使用 **UTF-16 code
unit** 计数。Rust 侧用 `encode_utf16().count()` 计算长度，切片用
`utf16_slice` 辅助函数，禁止字节索引。

**备选方案**：

  ---------------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- ---------------------------------------------
  字节偏移（Rust `len()`）            前端无法直接使用，中文和 emoji 下偏差大

  Unicode                             前端需要额外转换，代理对（emoji）下仍会错位
  标量偏移（`chars().count()`）       

  前端计算偏移传后端                  前端和后端各算一次，容易不一致
  ---------------------------------------------------------------------------------

**理由**：

1.  **前端零转换**：JS 字符串索引天然是 UTF-16，`text.slice(start, end)`
    直接可用。
2.  **后端可校验**：Rust 用 `utf16_slice`
    转成字节偏移后切片，结果与前端一致。
3.  **代理对安全**：emoji 在 UTF-16 下占两个 code
    unit，只要偏移不在代理对中间，切片就安全。

**后果**：

- Rust 侧所有偏移计算必须用 `encode_utf16().count()`，不能用
  `len()`，容易写错，需要测试卡住。
- `utf16_slice` 是导入模块的前置依赖，必须先写测试再实现。
- 与外部工具交换数据时，需要明确偏移口径。

**相关文档**：C4 第 3.1、8.3 节、D1 第 6.2 节、D3 第 3.4 节

### ADR-009 生词按 normalized 聚合，MVP 不做词形还原

**状态**：已采纳

**背景**：用户在阅读中可能多次遇到同一个词的不同形态（`run` / `running`
/ `ran`）。生词本需要决定按什么粒度聚合。

**决策**：MVP 按
`normalized`（小写、去首尾非字母数字、保留撇号和连字符）聚合，**不做词形还原**。`lemma`
字段留空。

**备选方案**：

  -------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- -------------------------------------
  词形还原（lemma）                   需要 NLP
                                      词典或模型，引入依赖和不确定性；MVP
                                      阶段投入产出比低

  按 surface 聚合                     `Run` 和 `run` 会变成两条，用户体验差

  按词根 + 词性聚合                   实现复杂，且语境义可能不同
  -------------------------------------------------------------------------

**理由**：

1.  **MVP 优先简单可靠**：`normalized` 规则确定，无外部依赖。
2.  **避免 AI/NLP 依赖**：与"不做 AI 解析"的定位一致。
3.  **可后续升级**：`lemma`
    字段已预留，未来接入词形还原时，在聚合层做映射，不改 token 结构。

**后果**：

- `running` 和 `run` 会被当成两个生词，用户可能觉得重复。
- 需要在产品文案中说明"按原词形态收录"，管理用户预期。
- 未来做词形还原时，需要处理已有数据的合并。

**相关文档**：C2 第 4.5、4.9 节、C4 第 7.2 节、D1 第 5.3 节

### ADR-010 导入不自动去重

**状态**：已采纳

**背景**：用户可能重复导入同一篇文章，或导入同一篇的不同版本。需要决定是否自动检测并合并。

**决策**：MVP **不做自动去重**。每次导入生成新的 `article_id` 和
`source_key`（UUID）。

**备选方案**：

  ------------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- ------------------------------------------
  按标题 + 正文 hash 自动去重         误判代价高：不同版本被合并会丢笔记或错位

  按标题去重                          同名不同内容会被错误拦截

  导入前强制用户确认重复              增加交互步骤，且检测逻辑本身可能误判
  ------------------------------------------------------------------------------

**理由**：

1.  **误判代价高于重复**：重复导入只是多一篇文章，用户可以手动删除；误合并会丢笔记，不可逆。
2.  **用户可能故意导入多版本**：不同来源、修订版、不同题目版本，自动合并会破坏用户意图。
3.  **MVP 简化**：去重逻辑需要额外的 hash
    计算和相似度判断，不阻塞核心闭环。

**后果**：

- 用户可能积累重复文章，需要手动删除。
- P1 可加"相似文章提示"，但不阻断导入（C4 第 10 节）。

**相关文档**：C4 第 10 节、A2 F5.5

## 6. 产品功能

### ADR-011 不做 AI 解析，笔记由用户自己写

**状态**：已采纳

**背景**：产品最初设想用 AI
生成句译、语法、短语、词义解析。评估后认为这会显著增加开发量、成本和不确定性。

**决策**：平台**不生成解析**。用户点句子、点单词看到的是自己的笔记编辑区。产品定位是"精读工作台"，不是"AI
解析器"。

**备选方案**：

  方案                   为什么没选
  ---------------------- ----------------------------------------
  AI 实时生成解析        慢、贵、不稳定、难审核，且用户点击要等
  AI 预生成 + 人工审核   需要内容生产流水线，个人项目维护不起
  平台人工写解析         24 篇 × 每句解析，工作量巨大，不可持续

**理由**：

1.  **成本归零**：没有 AI 调用费用。
2.  **质量可控**：用户自己写的笔记，不存在"AI 幻觉"。
3.  **版权风险降低**：平台不生产解析内容，只提供容器。
4.  **产品更轻**：开发量大幅下降，MVP 更快。

**后果**：

- 冷启动体验空：新用户打开文章，点句子看到空白输入框，可能不知道怎么用（A2
  F8 用引导缓解）。
- 学习效果依赖用户主动性：不愿意写笔记的用户会觉得产品"没什么用"。
- 差异化变弱：需要靠"精读结构 + 复习提醒"的顺滑度建立壁垒。

**相关文档**：A1 第 2.2 节、A2 F2.5、F2.6、F8

### ADR-012 不做做题判分，只展示题目和答案

**状态**：已采纳

**背景**：四级阅读材料通常带题目。产品需要决定是否支持用户作答、判分、记录正确率。

**决策**：MVP
只展示题目和选项，**选项不可选**，答案默认折叠，可展开查看。不记录用户作答。

**备选方案**：

  --------------------------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- --------------------------------------------------------
  支持作答和判分                      需要答题记录表、判分逻辑、正确率统计，增加复杂度和页面

  支持作答但不判分                    半成品体验，用户会问"我选的对不对"

  完全不展示题目                      失去阅读材料的完整性，用户需要另找题目
  --------------------------------------------------------------------------------------------

**理由**：

1.  **聚焦精读**：产品的核心是"读原文 + 写笔记"，做题是另一个场景。
2.  **降低复杂度**：无答题表、无判分逻辑、无正确率页面。
3.  **题目仍有价值**：用户可以先看题目了解文章主题，再精读原文。

**后果**：

- 用户如果想做题，需要另找工具。
- 未来若加作答功能，需要新增表和页面，但当前架构不阻塞。

**相关文档**：A1 第 7.2 节、A2 F2.4

### ADR-013 复习以篇为单位，不做纯单词间隔重复

**状态**：已采纳

**背景**：产品的定位是"通过阅读背单词"。复习机制有两种思路：按单词做间隔重复（如
Anki），或按整篇文章复习。

**决策**：复习以**整篇文章**为单位。到期提醒"该复习这篇了"，用户重新精读，笔记和高亮都在。不做单词级的间隔重复调度。

**备选方案**：

  ------------------------------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- ------------------------------------------------------------
  纯单词间隔重复                      脱离语境，与"通过阅读背单词"的定位冲突；需要复杂的调度算法

  单词 + 篇级双轨                     复杂度翻倍，MVP 不需要

  只做打卡提醒                        没有复习内容组织，用户不知道复习什么
  ------------------------------------------------------------------------------------------------

**理由**：

1.  **符合定位**：用户复习的是"这篇阅读里的单词、短语、语法"，不是孤立的单词卡。
2.  **实现简单**：篇级计划只需一张 `review_plan` 表，不需要单词级调度。
3.  **语境保留**：复习时看到原句和笔记，记忆效果更好。

**后果**：

- 复习一篇需要 10 分钟左右，比刷单词卡重，用户可能觉得负担大。
- 无法精确控制每个单词的复习频率。
- 未来若要做单词级调度，需要在现有结构上扩展。

**相关文档**：A1 第 5 节、A2 F4、C2 第 4.12 节

### ADR-014 复习间隔默认 1/3/7/14 天

**状态**：已采纳

**背景**：篇级复习需要一套默认间隔。候选包括艾宾浩斯曲线、固定间隔、用户自设。

**决策**：默认间隔 **1 天、3 天、7 天、14 天**，共 4 次。完成第 4
次后标记
`done`。用户可在设置中修改（P1）。"还需再看"不推进间隔，次日再提醒。

**备选方案**：

  --------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- --------------------------------------
  完整艾宾浩斯曲线（多次、密集）      篇级复习每次耗时较长，密集复习不现实

  用户完全自设                        新用户不知道设多少，默认值仍需要

  只提醒一次                          复习效果不足
  --------------------------------------------------------------------------

**理由**：

1.  **间隔递增合理**：符合遗忘曲线的基本规律，又不会太密集。
2.  **4 次可控**：一篇复习 4 次后基本巩固，不会无限提醒。
3.  **可调整**：默认值 + 设置项，兼顾新用户和进阶用户。

**后果**：

- 默认间隔不一定适合所有人，需要设置项兜底。
- "还需再看"不推进间隔，可能导致某些文章长期停留在同一间隔。

**相关文档**：A2 F4.2、C3 5.6 节

### ADR-015 内置 24 篇文章作为冷启动内容

**状态**：已采纳

**背景**：产品需要"打开就能读"的体验。用户自己导入文章门槛高，冷启动需要预置内容。2025
年两次四级考试共 6 套卷，每套 4 篇阅读，合计 24 篇。

**决策**：首批内置 **24 篇文章**（2025 年 6 月、12 月各 3 套卷 × 4
篇），按年份、套卷、题型组织。前提是拥有这些文章的著作权或已获授权。

**备选方案**：

  方案                       为什么没选
  -------------------------- --------------------------------------
  只做导入工具，不预置内容   冷启动太空，新用户第一篇不知道读什么
  预置更多文章               内容整理是体力活，24 篇足够验证
  预置自编模拟文             用户对"真题"有信任感，自编文吸引力弱

**理由**：

1.  **24 篇足够验证**：覆盖选词填空、长篇阅读、仔细阅读三种题型。
2.  **降低冷启动门槛**：用户打开就有内容可读。
3.  **可扩展**：后续可加六级、其他年份，结构不变。

**后果**：

- 内容整理和偏移量校验是体力活，需要在 M1 完成。
- 内置文章的升级需要 `source_key` + `text_hash`
  稳定识别，避免用户笔记错位（C2 第 4.4 节）。
- 需要保留内容授权记录（E3）。

**相关文档**：A1 第 7.1 节、C2 第 7 节、F1 M1

## 7. 发布与工程

### ADR-016 Android 不走静默更新

**状态**：已采纳

**背景**：Tauri 官方的 `tauri-plugin-updater` **不支持
Android**。Android 平台出于系统安全策略，不允许应用自行静默安装 APK
替换自身。

**决策**：Android 端采用"应用内检查版本 → 引导用户到 GitHub Release 页面
→ 手动下载 APK → 手动安装"的流程。使用 `tauri-plugin-android-update`
或前端请求 GitHub API 实现检查。

**备选方案**：

  方案                               为什么没选
  ---------------------------------- -------------------------------
  假设 updater 插件在 Android 可用   平台限制，不可行
  自建更新服务推送 APK               有服务器成本，与 ADR-002 冲突
  Android 不提供更新检查             用户不知道有新版本

**理由**：

1.  **尊重平台约束**：这是 Android 的系统限制，不是配置问题。
2.  **成本为零**：GitHub Release 页面就是下载入口，不需要额外服务。
3.  **用户体验可接受**：个人开源工具的更新频率不高，手动下载可接受。

**后果**：

- Android 用户更新需要几步手动操作，不如桌面端顺滑。
- 需要保证 `latest.json` 的版本号同时服务于桌面和
  Android，三处版本号必须一致（C5 第 3.3 节）。
- Android APK 签名使用独立 keystore，与桌面 updater 密钥分开管理。

**相关文档**：C5 第 3 节、D1 第 10.2 节

### ADR-017 不做 E2E 自动化测试

**状态**：已采纳

**背景**：项目需要测试策略。候选包括单元测试、集成测试、E2E
自动化（Playwright 等）、手动验收。

**决策**：MVP **不做 E2E 自动化测试**。Rust
侧用单元测试和集成测试覆盖数据层、导入、复习推进；前端只测 `api.ts`
封装和工具函数；页面交互、跨平台差异、自动更新用手动验收。

**备选方案**：

  ---------------------------------------------------------------------------
  方案                                为什么没选
  ----------------------------------- ---------------------------------------
  Playwright E2E 覆盖主流程           Tauri 桌面 E2E
                                      工具链不成熟，配置和维护成本高

  只做 E2E，不做单元测试              导入解析和偏移校验需要细粒度测试，E2E
                                      覆盖不到

  追求高覆盖率                        个人项目，覆盖率数字意义有限
  ---------------------------------------------------------------------------

**理由**：

1.  **核心逻辑已被单元测试覆盖**：切句、分词、偏移、事务、复习推进都有测试。
2.  **E2E 投入产出比低**：Tauri 桌面 E2E
    的配置成本高于收益，手动验收更快。
3.  **个人项目节奏**：测试跟着里程碑走，关键路径有测试即可。

**后果**：

- 页面交互回归依赖手动，改 UI 后需要人工走查。
- 跨平台 WebView 差异无法自动发现，需要在 Windows/macOS/Android
  手动验证。
- 未来若团队扩大或功能变复杂，需要补 E2E。

**相关文档**：D3 第 2 节、F1 各里程碑验收
